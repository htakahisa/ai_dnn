# coach_v1 v1 確定設計

## 1. 文書の位置づけ

本書は `coach_v1` の実装契約である。背景と学習方針は
`01.MODEL_DETAIL.md`、実装順序は `02.ALL_TASKS.md` を参照する。
記述が競合する場合は、本書の確定事項を優先する。

対象は現在の 26 行 × 44 列の固定マップだけとする。マップ、警戒ポイント、
固定ロスター、観測または行動の互換性が変わった場合、該当checkpointは再学習する。

## 2. v1の境界

### 2.1 v1で実装するもの

- attacker用coach 1モデルとdefender用coach 1モデル
- coachによる味方5人全員の上下左右移動、停止、PLANT、DEFUSEの決定
- キャラクター固有モデルによる8方向facing、通常アビリティの使用有無と対象地点の決定
- 味方5人の合法な視認情報を共有した `TeamPerceptionSnapshot`
- tick付きのクリア履歴、敵最終目撃履歴、警戒ポイント確認履歴
- 警戒ポイント中心の敵配置（初期70%／周辺20%／合法ランダム10%）
- actorとcentralized criticの入力分離
- tick開始時の共通スナップショットからの5人分一括推論と、そのtick中の結果キャッシュ

### 2.2 v1では実装しないもの

- ULTIMATEの選択・実行
- オーブ取得の選択・実行
- 新しいマップへの汎化
- BFS、A*、決め打ちルート、警戒ポイントへの自動誘導などの推論時経路探索
- 敵位置や衝突に応じた手書きの戦術分岐
- 警戒ポイント候補の自動採用
- 5人同時衝突を手書きで最適化する処理

ULTIMATEとオーブはゲーム機能として存在していても、coach_v1 v1のaction spaceには
含めない。既存game logicによる強制効果（被弾後の強制facingなど）はゲーム状態として
受け入れる。

## 3. 固定ロスターと順序

v1の固定ロスターは既存プリセット `Gorigons` とし、次の順序をモデル上の
slot順として固定する。

| slot | character | role | 通常ability | checkpoint id |
|---:|---|---|---|---|
| 0 | ごりまる | スモーカー | SMOKE | `gorimaru` |
| 1 | ごんごん | タイガー | HUNT（通常active abilityなし） | `gongon` |
| 2 | ごんた | シーカー | RECON | `gonta` |
| 3 | くんた | フラッシュ | FLASH | `kunta` |
| 4 | くりまる | フラッシュ | FLASH | `kurimaru` |

同じ5人でも順序を変えない。死亡者もslotを詰めず、そのslotをpaddingしてaction maskで
行動不能にする。陣営交代後もslot順は維持する。ロスターを変える場合は観測互換性を
破る変更として観測versionを上げ、キャラクター固有checkpointとcoach checkpointを
すべて再学習する。

## 4. 座標、tick、facing

- 座標は常に `(row, column)` とする。
- 移動差分は `N=(-1,0)`, `E=(0,+1)`, `S=(+1,0)`, `W=(0,-1)` とする。
- facing順は `N, NE, E, SE, S, SW, W, NW` とする。
- 通常視野は正面を中心とする半角90度、合計180度とする。境界の90度を含む。
- 通常視野に距離上限は設けない。壁、smoke、マップ境界で遮断する。
- clear対象は歩行可能マスだけとし、壁とsmokeセル自体はclearにしない。
- blind中の味方は通常視野によるclearと敵発見を生成しない。ただし味方RECON由来の
  チーム共有情報は受け取れる。
- tickは `current_round` と、LIVE中は `battle_tick`、defender setup中は
  `defender_setup_ticks_remaining` の組で識別する。

通常LOSの壁・smoke判定は既存ゲームのBresenham射線規則と一致させ、その後にfacing
条件を加える。RECONで現在reveal中の敵は、既存ゲーム仕様どおり壁・smoke・facingに
関係なく、そのRECONを使用したチームへ共有する。

## 5. 責任分担

### 5.1 coach

coachだけが次を決める。

- 5slotそれぞれの `STAY / MOVE_N / MOVE_E / MOVE_S / MOVE_W`
- `NONE / PLANT / DEFUSE` の目的行動
- キャラクター固有モデルへ渡す戦術意図

戦術意図は `HOLD, ADVANCE, ENTRY, SUPPORT_ENTRY, WAIT_TEAM, CLEAR_AREA,
MULTI_PEEK, RETREAT, UTILITY_REQUEST` の9値とする。これは通信ラベルであり、
推論側の固定行動へ変換しない。

### 5.2 キャラクター固有モデル

各キャラクター固有モデルだけが次を決める。

- 8方向facing
- 通常アビリティを使用するか
- 使用する場合の対象マス

キャラクター固有モデルは移動先、PLANT、DEFUSEを変更できない。通常アビリティは
各キャラクターにつき1ラウンド1回で、対象外・壁・範囲外・射程外などゲーム上不可能な
候補だけをaction maskする。タイガーの `HUNT` は既存ゲームに通常active abilityがないため、
ごんごんの通常ability使用actionは常にmaskし、facingだけを学習対象とする。

### 5.3 最終行動の優先順位

各slotについて毎tick、次の順で一つの行動を確定する。

1. 死亡、行動不能、ゲームによる強制拘束があればゲーム制約を適用する。
2. coachの目的行動が合法な `PLANT` または `DEFUSE` なら、その目的行動を行う。
3. それ以外はキャラクター固有モデルの通常アビリティ判断を使う。使用する場合はそのtick移動しない。
4. 通常アビリティを使用しない場合はcoachの移動を使う。
5. facingはキャラクター固有モデルの出力を適用する。ただしゲームによる強制facingを優先する。

PLANTとDEFUSEは完了まで毎tick coachが再選択しなければ中断する。無効なPLANT、
DEFUSE、アビリティを別行動へ戦術的にフォールバックしない。不可能な候補はaction maskで
防ぎ、なお発生した場合はその場停止として記録して学習上の無効行動に数える。

## 6. チーム観測の安全境界

### 6.1 actorへ渡してよい情報

- 固定マップと警戒ポイント
- 味方5人の位置、facing、生死、HP、通常アビリティ残数
- 自チームのspike所持者
- 公開済みのdrop済みspike位置、planted位置と状態、公開timer
- smokeなど盤面上で公開されている効果
- 味方の誰かが現在合法に視認している敵のIDと報告位置
- 敵の公開済み生死情報
- belief memoryに保存された最終目撃位置と経過tick
- 現在clearマスク、最終clearからの経過tick、各地点を現在見ている味方人数
- phase、side、人数、coachからキャラクターへの戦術意図

敵の現在HPと未確認のspike所持者はactorへ渡さない。

### 6.2 actorへ渡してはいけないもの

- 未視認敵の現在またはぼかした現在座標
- 生の `game_state["chars"]`
- `PerceivedGameView`、`PerceivedCharacter`、実ゲーム、実Character
- `PerceivedGameView.real_game`、`PerceivedCharacter.real_character` など実体への参照
- critic専用テンソル、critic用の敵実座標
- センサー判定後に未視認敵の実位置から計算した距離、方向、ヒートマップ

生のゲームオブジェクトへ触れてよいのは観測境界の `TeamPerceptionBuilder` と、学習時の
`CriticObservationBuilder` だけとする。actorへはコピー済みの数値配列と不変DTOだけを
渡す。actor APIは実体参照を保持しない。

### 6.3 視認とチーム共有

通常の敵目撃は、少なくとも1人の生存味方について次をすべて満たす場合だけ生成する。

1. その味方がblind中ではない。
2. 敵が前方半角90度以内にいる。
3. 壁とsmokeを考慮した既存LOSが通る。

味方RECONがrevealしている敵も目撃として扱う。資格判定より前に敵位置へIQ誤差を
加えてはならない。まず実座標をセンサー内部だけで使って視認資格を判定し、資格のある
viewerの報告だけに既存IQ品質相当の誤差を適用して共有する。複数報告がある場合は
`effective_iq` が最大のviewer、同値ならslot番号が小さいviewerの報告を採用する。

未視認敵については、敵IDと公開済み生死以外の現在情報をsnapshotへ生成しない。
味方全員の合法な目撃は同じtickのチームsnapshotへ統合し、全5slotが同じ内容を使う。

### 6.4 clearとbelief

- `currently_visible` はそのtickの味方通常視野の和集合とする。
- clear履歴は歩行可能な `currently_visible` マスだけを更新する。
- 敵目撃は該当敵の `last_seen_position` と `last_seen_tick` を更新する。
- clear ageとlast-seen ageは固定閾値で安全・危険へ変換せず、経過tick値としてactorへ渡す。
- 再確認したマスのclear ageは0に戻す。未確認中は増加する。
- 最終目撃は敵の実位置へ追従せず、再び合法に目撃したときだけ更新する。
- ラウンド開始時に全beliefをresetする。

情報漏洩テストの基準は、「合法な履歴が同一で未視認敵の実位置だけが異なる二状態から、
同一のactor観測が生成されること」とする。critic観測はこの比較対象から明確に分離する。

## 7. coachのtick実行契約

チーム実行コーディネーターは、各sideのそのtick最初の `decide_move` 呼び出しで次を行う。

1. その時点のチーム共通snapshotを一度だけ作る。
2. coachを一度だけforwardし、5slot分の出力を得る。
3. 5slot分を `(round, tick-key, side)` でcacheする。
4. 同じtickの残り4人は同じsnapshot由来のcacheを読む。

キャラクター処理後の座標を同tickのcoach入力へ足さない。cacheはround変更、side変更、
setup終了、明示resetで破棄する。既存コントローラーが1人ずつ呼ばれる構造には、
`team_ai.py` 側で「独自に安全なチーム知覚を処理するcontroller」をwrapper対象外にする
非coreの接続口をTask 10で追加する。actorへ生ゲームを渡さず、コーディネーター内の
センサー境界だけが参照する。

## 8. 観測・行動・checkpointのversion

初期versionを次で固定する。

| 対象 | 値 |
|---|---|
| checkpoint schema | `coach-checkpoint-v1` |
| coach actor observation | `coach-observation-v1` |
| coach action | `coach-action-v1` |
| character observation | `character-observation-v1` |
| character action | `character-action-v1` |

文字列はcheckpoint metadataへそのまま保存し、完全一致しなければloadを失敗させる。
channel追加・削除・並べ替え、shape、正規化、slot順、意味、action index、mask意味の変更は
該当versionを上げる。説明文、ログ、学習率など互換性に影響しない変更では上げない。

全checkpointに少なくとも次を保存する。

- schema、観測version、行動version
- 正規化された `NEW_MAZE_STR` のSHA-256 map hash
- 警戒ポイント設定のcanonical JSON SHA-256 hash
- 固定ロスターとslot順、対象characterまたはside
- model構成、学習seed、学習step、作成時刻
- state dictとoptimizer再開情報

hash不一致を黙って許可するoptionは推論側に設けない。

## 9. checkpoint構成

coachは同じnetwork実装を使うが、sideごとに完全に分離する。

- `checkpoints/coach/attacker/best.pt`, `latest.pt`
- `checkpoints/coach/defender/best.pt`, `latest.pt`

carry、escort、retrieve、guard、search、retakeごとのcheckpointは作らず、phaseを観測へ
含める。キャラクター固有モデルはsideとphaseを観測へ含む1人1checkpointを基本とする。

- `checkpoints/characters/gorimaru/best.pt`, `latest.pt`
- `checkpoints/characters/gongon/best.pt`, `latest.pt`
- `checkpoints/characters/gonta/best.pt`, `latest.pt`
- `checkpoints/characters/kunta/best.pt`, `latest.pt`
- `checkpoints/characters/kurimaru/best.pt`, `latest.pt`

性能不足が計測された場合だけ、将来の別設計versionでside別character checkpointを検討する。

## 11. core変更判断

Task 00ではcore変更は不要であり、変更しない。現時点の設計も次の方法でcore変更なしに
実現可能と判断する。

- 既存の1人ずつのcontroller APIは非coreのcoordinator cacheで5人一括計算へ変換する。
- 壁・smoke・facing視認は既存の公開状態とLOS規則から専用センサーで生成する。
- PLANT、DEFUSE、通常ability、facingの既存戻り値形式を使用する。
- coach専用wrapper接続はcoreではない `team_ai.py` で行う。

代替案としてcoreへチーム単位callbackを追加する方法もあるが、既存全controllerへの影響が
大きいため採用しない。後続タスクで既存公開状態だけでは合法観測を再現できないことが
テストで証明された場合に限り、別タスクで理由、影響、代替案を提示してから検討する。
