# coach_v1 実戦・分析・再学習の反復タスク

## 目的と開始条件

Task 00～17（[02.ALL_TASKS.md](02.ALL_TASKS.md)）の実装・統合評価が終わった後、実戦で見つかった課題を検証可能な学習変更へ変え、候補モデルを比較してから採用する。1周を `R001`、`R002` のような反復IDで管理し、採用しなかった試行も記録する。

基本の流れは **評価計画 → 実戦 → ログ検査 → 定量分析とリプレイ確認 → 改善仮説 → データ・学習変更 → 再学習 → 独立評価 → 採用判断 → 次の実戦**。実戦ログは問題発見の材料であり、そのまま正解ラベルや学習データとはみなさない。勝敗だけから原因を決めず、リプレイの該当局面とゲーム内で実際に起きた結果を照合する。

初回だけ Task R00 を行う。以後は Task R01～R09 を1周として繰り返す。各タスクの実行依頼には [11.REBUILD_template.md](11.REBUILD_template.md) をコピーして使う。各周の成果物は、たとえば `coach_v1/rebuild_runs/R001/` のようにIDでまとめ、対象試合・checkpoint・レポートを参照できるようにする。大きなリプレイや学習成果物は既存保存場所に置き、成果物には参照パスを記す。

## 共通の約束

- 比較対象の現行モデルを固定し、attacker coach、defender coach、キャラクター5人の実際に読み込んだ checkpoint のパスとSHA-256、コード版、マップ・警戒ポイント hash、観測・行動 version を記録する。`best.pt` のような可変名だけを証跡にしない。
- 評価用 seed・相手・陣営・試合数・主指標・採用条件を候補の学習前に決める。候補と現行は同条件で対戦し、陣営を入れ替えて比較する。学習や調整に使った試合と、最終採用判定に使う試合を分ける。
- 勝率は試合数と勝敗数を併記する。attacker/defender 別、相手別、phase 別にも集計し、分母の小さい差は断定しない。補助指標だけ改善しても、勝率や重大な退行を確認する。
- 実戦結果と replay の真の状態は事後解析・評価に使える。actor の観測や推論側へ未視認敵の実位置を渡さない。teacher や critic に真の状態を使う変更は、既存の情報境界と学習仕様を確認して明示する。
- 一周で扱う主仮説は原則1つ。複数変更が必要なら個別比較か ablation を計画する。実装・接続・計測の不具合は学習の問題と分けて修正し、修正前後を同一モデルの性能比較として扱わない。
- 現行の正式 checkpoint は候補評価が終わるまで保持する。未達の候補は採用せず、理由と次の仮説を残す。`latest` を自動採用しない。

## Task R00：反復基盤の確認（初回と計測仕様変更時）

目的：Task 14～17 の実戦・保存・評価経路を、反復で再利用できる状態にする。

実施内容：
- `coach_v1` が実戦で正しい side 別 coach と5人の character checkpoint を読み込む経路を確認する。未接続なら、その接続を別実装タスクとして完了させる。
- 対戦ツールの結果形式と保存先を確認する。大会管理側の結果には `round_records`、`replay_frames`、seed などがある一方、`run_headless_series.py` の簡易結果は主にスコア集計である。分析項目に必要なデータがどの経路で得られるか、サンプル1試合で確認する。
- `TeamExecutionCoordinator.action_log` は要求行動のメモリ内記録であり、ゲームが受理・実行した行動の証明ではない。必要な場合、試合ID・round・tick・side・slot で実ゲームのイベントや replay と突き合わせて保存できるようにする。
- 解析器の入力 schema、欠損の扱い、主要指標の定義と分母、試合IDから replay の該当 round/tick へ飛べる参照方法を決める。既存の `analytics/` を再利用できる箇所は再利用する。
- 固定 seed での再現、ログと勝敗の一致、陣営交代、未視認情報の遮断、checkpoint metadata の互換性を確認する。

完了条件：coach_v1 を含むフルマッチ1件について、モデル版・seed・勝敗・round・replay が追跡でき、定義した主要指標を計算できる。欠ける項目は「未計測」として明記し、必要な計測実装を先にタスク化する。

## Task R01：今回の評価計画を固定

目的：結果を見てから評価条件を変えないようにする。

実施内容：
- 反復ID、現行モデル、対象マップ、対戦相手プール、seed 群、陣営配分、試合数を記録する。
- 主指標と採用条件を決める。例：相手別・side 別勝率、plant 成功率、retake 成功率。単独突入率、trade、ability 有効率、無効行動率などは診断用として定義する。
- 探索用の試合群と、候補の採用判定まで開かない独立評価群を分ける。既存 `omoko_v1`・`touyama_v2`・`gc_v1`・過去 coach_v1 checkpoint のうち、利用可能な相手を明記する。

完了条件：評価プロトコルと採用・保留・不採用条件が試合前に記録されている。

## Task R02：現行モデルで実戦し証跡を保存

目的：再現可能な実戦結果を得る。

実施内容：
- R01 の条件でフルマッチを実行し、対戦結果、round 記録、必要な replay、実際の checkpoint 版を保存する。
- 試合ごとに相手・seed・初期陣営・最終結果・ファイルパスを一覧にする。失敗・中断した試合も残し、再実行理由を記す。

完了条件：予定試合数と有効試合数を照合でき、各試合から replay へ到達できる。欠損があれば追加実戦または R00 の計測修正へ戻る。

## Task R03：ログと評価母集団を検査

目的：誤った集計や欠損から誤診しない。

実施内容：
- 重複試合、seed の重複、途中終了、side の取り違え、checkpoint 混在、round 数と最終スコアの不一致、replay の欠落を検査する。
- 行動を分析するときは「モデル要求」「ゲーム受理」「実際の位置・効果」を区別する。ログにないイベントは推測で補わない。
- 除外試合と理由、集計に使った試合IDを固定する。

完了条件：有効試合の一覧と除外理由が残り、主要指標の分母を再計算できる。

## Task R04：定量分析とリプレイ診断

目的：良い行動と悪い行動を局面単位で見つける。

実施内容：
- 全体・side・相手・phase・キャラクター別に R01 の指標を集計し、現行/過去モデルとの差と試合数を示す。勝った局面も調べ、維持すべき強みを記録する。
- 苦手地点候補、繰り返す敗因、無効行動、単独突入、過剰ローテーション、護衛不足、能力のタイミングなどを候補として抽出する。Task 16 の候補レポートを使える場合は参照する。
- 代表的な成功例・失敗例・反例を replay で確認する。試合ID、round、tick、局面、観測可能だった情報、要求行動、実結果を記録し、原因は「確認済み」「仮説」「判断不能」に分ける。

完了条件：数値と具体的な replay 参照の両方を伴う改善候補一覧があり、単発の印象を一般化していない。

## Task R05：改善仮説と学習変更を選ぶ

目的：診断を検証できる1件の変更に落とす。

実施内容：
- 対象を coach の移動・意図、特定 character の facing/ability、警戒ポイント、シナリオ分布、reward、curriculum、接続バグなどに切り分ける。
- 「どの局面で何が改善するか」「何が悪化しうるか」「どの指標と replay で判定するか」を書く。学習不要な計測・接続バグなら修正経路へ回す。
- 実戦ログから教材を作る場合は、局面抽出、ラベル根拠、重複排除、学習/検証/独立評価の分割を明記する。勝った行動を無条件に正解としない。警戒ポイント候補は Task 16 の方針どおり自動追加しない。
- 対象外のモデルと評価条件を固定し、必要な変更・再学習範囲を決める。map/point hash、観測/行動 version が変わる場合は [03.DESIGN.md](03.DESIGN.md) の互換性規則に従う。

完了条件：変更前後の差分案、データ出自、成功・失敗条件、対象 checkpoint が明確である。

## Task R06：候補を再学習しオフライン検証

目的：仮説どおりに学習でき、既存契約を壊していない候補を作る。

実施内容：
- R05 の変更を実装し、seed、データ分布、学習設定、開始 checkpoint、学習履歴、候補 checkpoint を保存する。
- 固定の検証局面と警戒ポイント周辺・ランダム配置を含む局面で、対象指標と退行指標を確認する。対象外モデルの checkpoint は固定する。
- 観測/行動互換、合法行動 mask、未視認敵情報の遮断、学習と推論の入力一致を確認する。

完了条件：再現可能な候補と検証結果があり、不整合や明白な退行がない。失敗時は設定・結果を記録して R05 へ戻る。

## Task R07：同条件の実戦比較

目的：オフライン改善が実戦でも成立するか確かめる。

実施内容：
- 現行モデルと候補を、R01 で確保した独立 seed・相手・陣営条件でそれぞれ実戦させる。評価途中で条件や採用基準を変えない。
- 全体勝敗と side/相手/phase 別の指標、改善を狙った局面、重大な退行を比較する。試合数・分母・ばらつきと、代表 replay を添える。
- 差が小さい、試合数不足、相手依存などの場合は「判断保留」とし、追加評価の条件を明記する。

完了条件：現行対候補の同条件比較表と、採用基準ごとの判定がある。

## Task R08：採用・保留・不採用を決定

目的：勝率や戦術の改善を失わずに正式モデルを更新する。

実施内容：
- R01 の条件に照らして判定する。採用時は旧正式 checkpoint と評価レポートを保持し、正式参照を候補へ切り替え、ロードテストと短い実戦確認を行う。
- 保留/不採用時は現行を維持し、失敗した仮説・次回の調査項目を記録する。Task 15 の opponent pool と Task 17 の比較評価に照らして相手別退行を確認する。

完了条件：正式 checkpoint と採用理由を再現でき、元に戻せる。判断不能を採用扱いしない。

## Task R09：反復を締めて次の周を始める

目的：知見を蓄積し、次回に同じ調査を繰り返さない。

実施内容：
- 試合一覧、解析、成功/失敗例、変更差分、学習履歴、独立評価、採否、残課題を反復IDでまとめる。
- 次周の基準モデルと最優先課題を1件決める。採用モデルに対する新たな実戦は新しいIDの R01 から始める。

完了条件：第三者が「何を見て、何を変え、どう比較し、なぜ採用したか」を追跡できる。
