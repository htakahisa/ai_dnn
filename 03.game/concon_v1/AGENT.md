## 基本方針
- 可能な限りコード、ドキュメントは分類してディレクトリに配置する。ただし、ディレクトリ階層が深くなりすぎたりして余計わかりにくい構造は避けること。
- テストコードは test ディレクトリ以下に配置すること
- ドキュメントはこの AGENT.md を除き docs 以下に配置すること。まとまりがよくなるなら、サブディレクトリ作成も行うこと。
- 学習用スクリプトの自動実行はしないこと。学習はこちらで手動で時間を見て行うため。
- token の消費はなるべく抑える形で対応したいので、出力、入力についてこちらで制御できる分については効率よく行うこと。特にログ出力などは必要なものをきちんと取得して対応すること。ただ、token消費を抑えるため、データが足りず調査に余計にtokenを使うような愚かな真似は許さない。

【前提】
・機械学習については、基本的に行動は学習によって対応し、推論側にロジックを入れて行動を制御することは可能な限りせずに、学習させた結果として行動させるようにする。
・ゲームのcore となるファイルはabilities_los.py, battle_logic.py, game_core.py, map_data.py, map_data_defender_setup.py, run_game.py
あたりです。
・基本的には、coreのファイルの修正は不要な認識で、明確な仕様変更、バグがあるときのみ修正対象とします。
・学習用の train ファイルと、推論用の learning ファイルについては、それぞれ対になっているため、例えば、 train_carry.py は learning_carry.py に import してOKです。
ただし、train_carry.py を 別の推論の learning_guard.py 等への import は禁止します。


【説明】
このプロジェクトでは、valorant を上から見たようなゲームを作成しています。
5v5で、それぞれグリッドのマスを1tick に一度移動したり、アビリティ(smoke, recon, flash)を使用できます。
ルールはvalorant と同じで、attacker, defender がいて、スパイクをプラントしたり、解除したりというものです。キャラは8方向を向くことができます。

このゲームをAIに学習させて移動させたり、アビリティを使用したりさせたいです。
射撃は自動で行われるので、AIがするのは、移動とアビリティの使用のみです。

アビリティは1 round に 1回だけ使用できます。各キャラにつき1種類のアビリティのみ使用可能です。

マップのデータは map_data.py にあり、 0が床、1が壁(壁は移動不可能)、2がスパイク配置可能な床、3がattacker の配置位置、4がdefender の配置位置です。

## 5人のキャラ共通のモデル作成の仕様について
attacker の場合は以下の phase があります。

1. carry phase : スパイクを運ぶフェーズ。A1, A2 などいくつかの攻撃パターン用のモデルがあります。
2. retreive phase : 落ちたスパイクを拾いに行くフェーズ。(ますが重なれば自動で拾う)
3. guard phase : 配置したスパイクを解除されないように守るフェーズ。主に位置取りとアビリティの使用が重要。
という形です。 

defender の場合は以下のphase があります
1. search phase : 所定の防御位置に移動し、敵を待ち構える。敵またはスパイクを見つけたらそちらに移動を開始し、戦闘、アビリティの使用を行いスパイクの設置を阻止する。
2. retake phase : プラントされたスパイクを解除する。単体で突入するとやられやすいので、人数がそろうのを待ち複数人でアビリティを使用しながら突入してスパイクの解除を行う。

## 目的について -重大事項-
1. attacker の目的は勝利すること。スパイクの設置から起爆までガードすること。および、敵の全滅による勝利が目的。スパイクの設置のみ、敵の全滅の、を目的にしたコードの修正を禁止する。敵全滅が確率的に高いのであれば敵全滅を目指し、スパイク設置の可能性が高いならスパイク設置を目指すものとする。
2. attacker の第一目的は、安全にスパイクを設置場所まで運び設置することです。目的のために経路の迂回や、味方に道を譲ることははあっても、それが目的ではありません。目的はスパイクを設置すること。敵を倒すこともその目的があるからこその対応です。目的を誤り、馬鹿な修正をすることを禁止する。言われたことだけ対応する修正はattacker の目的を無視した極めて許しがたい行為である。禁止事項として挙げる。
3. attacker の第二目的は、プラントしたスパイクを防御し、defender からの解除を阻止することである。そのためには有利なポジションで待機し、敵が来るであろう場所にあらかじめfacing したり、アビリティ、ウルトを使用して接近の遅延、有利な交戦を行う必要がある。ポジションとfacingは特に挟撃が有効であるため重要項目である。スモークに隠れてスパイクの解除をするディフェンダーもいるため、スモーク内でスパイク解除音がした場合は外から射線が通らないためすぐにスパイク方面に移動し、解除している敵を射撃する必要がある。

## attacker について
1. マップに沿って移動し、指定の場所を追加してサイトに進む。a,b,c,d・・の順に進んでいく。小文字が2つある場合は 0,5、5,0、2,3、3,2 に分かれて進む。大文字が2つある場合は 2,3、3,2 のみとなり、固まることを防ぐ。

## 敵との交戦時の挙動について
1. 敵と射撃の交戦が始まった場合、移動しながら射撃すると射撃精度が極端に落ち、打ち合いにおいてかなり不利になるたる敵を視認した場合は停止して射撃する必要がある。ただし、相手がフラッシュやウルトを受けて命中精度などが落ちている場合は、効いている相手に射線を通すようにどんどん進むことを推奨します。狭い通路で一人が後ろの移動を妨げているとせっかくのフラッシュが効いているチャンスなのに先頭の一人しか射線が通らずに敵を倒せないことを避けるためです。ただし、フラッシュを食らっている敵の真横は通常の命中率とほぼ変わらない状態になるため、1マス以上は上げる必要があります。

## 修正について
1. 修正においてはまず「目的」が第一優先。指示をそのまま適用し、目的を無視した修正は禁止する。何のための修正かわからないため。「目的」の意図を理解せずに修正することを全面的な禁止事項とする。修正の指示が「目的」と合わなくなる場合は必ずその旨を報告しそのまま進めてよいか確認する。絶対行わなければならない。
2. 修正はお願いしますが、学習スクリプトの実行は不要です。こちらで実行し、動作確認し、結果をもとに再び連携します。時間がかかるのでこちらで対応するものです。
3. 新規に作成するファイルはすべてこのディレクトリ以下に配置します。ルートディレクトリやその他の場所にこのディレクトリ内で使用するファイルは配置しません。すでにあるファイルの修正はそのまま修正すればよいですが、新規に作成され、またこのディレクトリ専用のものであればこのディレクトリは以下に配置すべきです。
4. 学習にはIQ知覚を実装すること。本番での処理と同じ状態で学習しないと意味がないため。co1_train_attacker.py 等を参考にすること。
5. 各プロジェクト用のスクリプトは、実行ルートはそのプロジェクトディレクトリです。03.game ではありません。プロジェクト専用のスクリプトは、そのプロジェクトのディレクトリから実行でするようにパス指定しなければなりません。
6. モデルのDQNで使用する値として最低限必要なのは「MAPの情報」「味方の位置」「敵の位置(視認した敵の位置は味方内で共有する)」「facingの向き」です。特に「敵の位置」と「facing」は重要で、味方からの共有情報で敵の位置が分かっている場合は、あらかじめ敵の方向を向きながら移動などして敵と交戦するほうが有利となります。ただし、あえてその情報を含めていないケースも存在するため、勝手に足りないからという理由での修正を禁止事項とする。修正前には必ず確認すること。
