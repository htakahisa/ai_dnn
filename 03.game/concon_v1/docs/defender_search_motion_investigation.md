# defender search の往復移動の調査（2026-10-05）

## 調査後の修正

ユーザーの修正指示を受け、以下の処理を変更した（reward_version=7）。

- IQ知覚の死亡情報から、共有記憶の死亡フラグを更新する。IQによる視認漏れは死亡と誤判定しない。
- 生存敵の記憶だけをsearchの継続条件にする。撃破者の6 tickの警戒は別途保持する。
- 既存の撃破状態の入力を警戒中にも維持し、停止・照準を学ぶ補助損失を警戒中に適用する。入力の次元を増やさない。
- 生存敵の最後の位置の記憶だけがある帰還中は、配置用の学習済み移動を教師としてsearch部分を訓練する。推論では移動を強制しない。
- 配置・援護目標から離れるか距離が縮まらない移動を追加減点する。敵を向く加点を得ても、2マスの往復で報酬が増えないようにする。
- bestの選択で撃破後警戒・記憶だけの帰還動作の悪化を拒否する。

学習とcheckpointの更新は実施していない。保存済みモデルの旧出力が修正後の訓練で変わることは、ユーザーによる再学習・評価が必要である。修正時点のマップと保存済みcheckpointの署名は不一致だったため、旧モデルによる修正前後の対戦比較は行っていない。テストでは現在のマップ用の参照配置テーブルを使い、学習スクリプトは実行していない。

以下は修正前の調査結果である。

## 結論

保存済みsearchモデルで往復移動を再現した。敵の情報がある間はsearchの追加ネットワークが行動を選び、敵の記憶が失効すると固定された配置用の重みが行動を選ぶ。このため、敵撃破・視認消失の後に複数人が往復し、時間経過後に所定の配置へ戻る。

## 「ベースへの追加学習」の実装

- `DefenderSearchBattleDQN` は配置モデル `DefenderSearchDQN` を継承する。
- 初回のsearch学習は配置checkpointの重みを読み込む。
- `navigation_values` と `navigation_yield_values` は固定される。
- search学習は追加された `encoder` / `head` を更新する。
- 保存済みsearch checkpointには配置用の重みと追加部分の重みが両方含まれる。
- `forward()` は敵の記憶・撃破後警戒が有効な場合に追加部分の出力を使い、それ以外とsetup中は配置用の出力を使う。追加部分の出力に配置用の出力を加算する実装ではない。

したがって、現在の実装は「ベースの配置行動全体を追加学習で更新する」方式とは異なる。

## 事象を引き起こす処理

`co1_defender_search_common.py` の `build_search_inputs()` は、敵の視認情報をcontrollerの共通 `sightings` に保存する。5人は同じcontrollerを使用する。

死亡が判明した記憶には `alive=False` を設定するが、`remembered` と `active` の判定はその死亡フラグで記憶を除外しない。死亡した敵の記憶だけでも追加ネットワークが有効になる。また、撃破者以外が倒した敵について、死亡したproxyを使って記憶の死亡フラグを更新する一般処理はない。

敵の最終視認から12 tickで記憶が消え、他の敵の記憶や撃破後警戒がなければ配置用の出力へ戻る。撃破時から必ず12 tick待つわけではなく、他の敵を視認すると継続時間も変わる。

searchの追加部分は、敵がいなくなった後の停止・帰還を十分に実現できていない。往復移動は追加部分が有効な区間の連続した推論で発生しており、モデル選択の毎tickの交互切り替えが原因ではない。

## 確認結果

2026-10-05の保存済みcheckpoint:

| ファイル | episode | reward_version |
| --- | ---: | ---: |
| co1_defender_search_best.pt | 750 | 6 |
| co1_defender_search_latest.pt | 1000 | 6 |

`runtime_model_path` は有効なbestを優先する。そのため、モデルを明示指定しない本番の読み込み先は750 episodeのbestである。

探索率0、seed=0、通常の5v5開始、IQ知覚ありで評価した。往復回数は、各defenderが「直前の移動元へ次の移動で戻る」事象の合計であり、全員同時の回数ではない。

| モデル | attacker | 往復回数 |
| --- | --- | ---: |
| best (750) | Fnatic v3 | 30 |
| latest (1000) | Fnatic v3 | 3 |

bestとFnatic v3の対戦では、battle tick 54でBoasterの記憶が死亡扱いとなり、その後も複数defenderが往復した。tick 55〜60では、例えば `[10,11] ↔ [11,11]` と `[9,12] ↔ [10,12]` の往復が発生した。この対戦では、死亡扱いの記憶だけでsearchが有効な行動判断が計34件あった。

独立した入力確認でも、死亡フラグを設定した敵の記憶を最終視認tick=0で保存すると、tick 1・6・11は `active=True`、tick 12は記憶0件で `active=False` となった。

bestの保存済み評価では、撃破後の停止・照準維持率は約25.6%。latestは約27.6%。1000 episodeという回数だけでは撃破後の行動が習得できたとは判断できない。

## 対応の方向

死亡した敵の位置をしばらく警戒すること自体は必要である。死亡記憶をすべて即座に捨てる修正だけでは、その目的を満たせない。生存敵への対応と撃破後の警戒を観測・学習で区別し、警戒時の停止と警戒終了後の帰還を学習・評価できるようにする必要がある。全員の移動を推論側で一律禁止する方法は採らない。

今回の作業は原因調査であり、学習・モデル保存・動作処理の変更は実施していない。

## 再現用スクリプト

`concon_v1` を作業ディレクトリとして実行する。

```powershell
python diagnose_defender_search_motion.py --models data/defender_search_data/co1_defender_search_best.pt data/defender_search_data/co1_defender_search_latest.pt --opponents fnatic_v3
```

このスクリプトは保存済みモデルを評価するだけで、学習しない。`--output docs/motion_trace.json` を指定すると各行動の記録を保存できる。
