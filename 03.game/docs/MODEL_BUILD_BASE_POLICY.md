# AIモデル構築の共通方針と、対戦行動の調査・修正から得た知見

更新日：2026-10-12。

attacker / defender の analysis・search・plant・retake・guard、新しいAIの作成・学習・評価・改修時に参照する。Touyama v3対FRCを中心に、危険経路、サイト入口、射線、アビリティ、教師、報酬、評価条件を調べた結果をまとめた。

**不具合の確認、コードの修正、教師の改善、学習済みモデルの実力改善は別々の段階である。** 本文の共通方針を他モデルへ適用する際も、そのモデルの実エンジン・観測・ケース・対戦で検証する。search / retake / guardへ同じ修正を適用して性能が上がった、という実績を意味しない。

各AIの個別AGENTS.md、ゲーム仕様、保存モデルの契約、ユーザーの指示を併せて確認する。過去の調査文書にある「次に学習する版」「学習保留」は当時の状態であり、現在の実行指示としてそのまま使わない。

## 1. モデルの責務と、共通して確認する情報

| モデル・段階 | 主な判断 | 共通して確認する内容 |
| --- | --- | --- |
| analysis | 敵配置・経路・サイト・成功や被害の予測 | 公開情報と記憶、候補の到達可能性、成功ラベルの意味、結果を生成した実行モデル、予測の較正 |
| attackerの接近・plant | 接近経路、入口、戦闘・投擲・設置 | サイトを横切る近道の誤用、選択経路と実際の目標、保持者と支援役、設置までの時間、設置後の人数関係 |
| defender search | 敵の探索・情報取得・迎撃位置への移動 | 未視認敵を不在と扱わないこと、射線・向き・占有、危険な探索経路、後のretakeへ引き継ぐ状態 |
| defender retake | サイト再進入、制圧、解除 | 接近と入口突破の区別、反撃可能性、投擲の有効時間、実際の解除可能範囲と所要時間、担当と支援の分担 |
| attacker guard | 設置後の配置・保持・解除阻止 | 残人数・HP・能力・位置からの実際の勝利、解除通知・公開接触への対応、遮蔽、同じ敵への支援、不要な再ピーク |
| defenderの保持段階 | 進入防止、配置維持、必要時の再配置 | 守る目的に対する配置・向き、敵への射線、退避路、味方占有、後続段階との接続 |

行動は基本的に、学習モデルが合法候補から選ぶ。BFS、射線計算、教師、目標割当は、到達可能性の確認・特徴量・行動候補・教師例を作るために使う。問題を見つけるたびに推論時の移動・停止・設置・能力を強制し、学習不足を覆い隠さない。

エンジン上の不可能な行動と、戦術的に危険な行動は区別する。壁・残数・移動阻害などの合法性と、危険度・勝てる見込み・温存の価値を同じmaskへ混ぜない。戦術上の制約を設ける場合は、その理由・条件・例外・候補消失を記録し、学習と通常推論で条件を一致させる。

## 2. 公開観測、記憶、射線を混同しない

### 2.1 敵が見えない理由を分ける

敵の不在、壁・煙・向きによる未視認、表示更新の遅れ、記憶の古さ、敵の死亡は別の情報である。「視界に入るマスなのに敵の表示がない」だけで、安全や敵不在を確定しない。

今回、幾何学的なvisible_cellsは現在の位置・向きを反映する一方、敵sightingは移動・射撃後に更新される表示状態を参照していた。直前にいた敵を、新しく見通せたマスに表示されないことだけで危険から外し、前進して死亡する例を確認した。

Touyama v3では、連続2tickの幾何学的視認と現在・直前の目撃を使い、確認済み空マスを別フィールドへ分離した。同じtickの5人分のencodeで履歴を重複更新せず、ラウンド・phase変更やtick欠落で確認をリセットする。通常の幾何学的視界まで書き換えない。

この「2tick」は当該エンジンの更新順に合わせた実装例である。他モデルでは先に観測・行動・移動・射撃・表示の更新順を調べ、意味に合った不在確認を定義する。

### 2.2 記憶には鮮度・失効条件を持たせる

公開目撃の位置・時刻・情報源を保持し、経過時間、死亡、確認済み不在、ラウンド境界で有効性を判断する。今回の戦闘記憶は最大20tickを用いたが、値を全モデルの固定仕様にしない。古い記憶を確実な現在位置として扱わず、目撃が途切れた瞬間に危険をすべて消すこともしない。

### 2.3 「撃てる」「撃たれ得る」「味方が動いた後」を分ける

敵がいる地域と経路の地域が重ならなくても、地域外から長い射線が通る。危険評価は地域の占有だけでなく、経路セル・入口・次の移動先から実際の壁・煙・身体遮蔽を確認する。

| 判定 | 意味 |
| --- | --- |
| outgoing / 反撃可能性 | 現在の公開状態で、自分から対象へ射撃できるか |
| incoming / 被射線 | 公開された敵位置から自分の候補位置へ射撃可能な線があるか。敵の非公開の向き・blind・命中を断定しない |
| unreturnable / 一方的な射線 | 被射線があるのに、こちらの反撃射線がないか |
| temporary cover | 現在の味方の身体が遮っているが、その味方が動くと通る可能性があるか |
| planned geometry | 味方の公開選択行動から予定位置を投影したときの射線。実移動成功の保証ではない |

全員の移動後に射撃するエンジンでは、現在の味方位置だけで安全と評価すると、そのtickに味方が離れて撃たれる。壁の持続的な遮蔽と、動ける味方の一時的な遮蔽を区別する。

今回のv16では、潜在的なincomingの判定では動ける味方の身体だけに依存しない一方、現在実際に撃ち返せるかの判定は身体遮蔽を保持した。潜在的な危険を追加しただけで無条件の退避・待機を教える案は、時間切れを増やして不採用になった。可能性を入力することと、現在撃たれていると断定して停止することは別である。

壁判定は実エンジンと一致させる。現行共通コードのwall_line_cells()は角に接する隣接セルも含む対称判定、WALL_LOS_VERSIONはsymmetric_supercover_v1。line_cells()とは用途が異なる。変更時は呼出元・観測・scenario・配置・依存モデルを確認する。

### 2.4 被リコン中のスモークを安全な壁と扱わない

今回、味方がRECONで検知されると、敵からは煙越しに撃てる一方、こちらは煙で敵を見られず反撃できない場面があった。これはゲーム仕様であり、壁LOSのバグと混同しない。

自分のreveal残時間を観測し、被検知中のincomingには煙による遮蔽をそのまま適用しない。outgoingは別に計算する。相手をこちらも検知している場合や隣接時の例外などは、実エンジンの仕様に合わせる。

被検知時は、合法な一歩、占有、壁陰までの複数歩、途中の被射線増加、残り時間を確認する。退避先を右下オーブなど特定座標へ固定しない。サイト外から退避する経路が、敵のいるサイト内を近道として横切らないようにする。教師の退避を集合待ちや無関係な投擲で上書きしない。

## 3. 経路、サイト境界、入口、目標を整合させる

### 3.1 地図の半面と、サイトそのものを区別する

左右半面の分類は厳密な設置可能床への所属判定ではない。サイト内部のセルを入口として記録したり、右半面の人数を右設置床の人数として報告したりしない。

入口はサイト外outsideからサイト内insideへの実際の境界で表す。選択入口、実際に横断した入口、保持者の横断、他の味方の横断を別々に残す。サイト内から始まる経路には「入口なし」を明示する。

### 3.2 サイト内部を使った近道に注意する

敵がいるかもしれないサイトの内部を通れば、別の入口への最短距離が短く見えることがある。しかし、その経路は入口まで安全に接近できる経路ではない。

接近・flank・退避の到達可能性は、その段階で通ってよい床を指定して計算する。反対側サイトや、接近中の選択サイト内部を除いた距離・経路を必要に応じて用いる。同じ除外条件を候補生成、役割割当、教師、距離特徴量、時間判定へ共有する。

「分岐d/b/hから入口Cへ向かう」という目標でも、許された接近経路で到達できなければ候補から外す。物理的・phase上の到達不能と、到達できるが危険な入口は別の理由として記録する。到達可能で危険な候補は、公開情報で評価・探索する余地を残す。

一律にサイト内移動を禁止する方針ではない。突入後、制圧後、設置後guard、retakeなどではサイト内部を移動する必要がある。目的・phase・現在の制圧状況に応じた経路計算が必要。

### 3.3 経路候補の存在と、実際の探索は別である

候補生成で複数経路があっても、同じ経路しか選ばれない、選んだ探索経路が維持処理で取り消される、局所行動のepsilonだけで経路を探索していない、という問題を確認した。

分岐列が同じでも、入口・遮蔽・セル列が違えば戦術上別の経路である。候補上限や重複除去がその違いを消していないか確認する。全経路を列挙していると誤解せず、生成方式・制限・除外理由を記録する。

経路探索と局所行動探索を別設定にし、低く誤評価した候補にも試行機会を与える。モードの重複で経路の抽選確率を増やさず、探索選択を通常のヒステリシスで即座に取り消さない。試行には歩数・時間・公開危険による終了条件を持たせる。探索のために危険な前進を強制しない。

要求経路、初期選択、選択継続、実移動列、実分岐列、実入口、最終サイトを別々に集計する。初期の選択回数だけで「別の経路を実行した」と結論しない。

### 3.4 同じサイトでも入口変更時に古い目標を解除する

安全側の右経路を選んでも、以前の外周入口の集合目標が残り、保持者を逆方向へ動かす不具合があった。サイト名だけをリセット条件にすると、同サイト内の入口変更を扱えない。

経路、outside/inside、役割目標、集合開始、通路制限を一緒に更新する。集合判断には選択経路上の入口までの残距離を使い、最寄り設置床への距離と混同しない。入口変更後の翌tickに古い目標を再割当しない。

初回から広く集合条件を変更した案は回帰し、入口変更時だけに限定した処理が改善した例がある。目標解除の範囲を限定し、既に機能している初期準備を壊さない。

### 3.5 安全な接近と、入口突破・制圧は別の能力

既知敵から射線のない接近路が見つかっても、別の敵が途中で現れることがある。接近だけ成功しても、入口で戦闘・支援・投擲・設置を実行できなければ時間切れになる。

危険だから右を一律に禁止したり、右3人なら無条件で左へ切り替えたりしない。公開の人数・位置・射線、別経路、能力、移動コスト、期限を比較する。普段の左成功率100%は、右で失敗したラウンドを左に変えても必ず成功することを意味しない。公開情報で知らない敵の真の配置を切替判断へ渡さない。

## 4. アビリティは、投げる位置・目標・効果時間まで設計する

### 4.1 敵座標への直接投擲だけでは候補が不足する

壁陰の特定位置から投げると、直接敵座標を狙った候補は無効でも、別の投擲目標なら複数敵へFLASHが届く例を確認した。着弾点は目標座標と常に一致するとは限らない。

実エンジンの投射終点、壁、飛行時間、作用範囲、煙、合法な目標を用いて候補を作る。発射位置・目標・着弾点・到達時刻・作用が見込める公開敵・期限を特徴量とログへ持たせる。候補がないことと、候補はあるがモデルが使用を見送ることを分ける。

### 4.2 連携は「使用回数」ではなく目的への作用で確認する

例として、敵の射線をSMOKEで遮り、露出した敵へFLASHと味方の射撃を合わせ、煙内の敵をRECONで検知してから射撃する連携を検討できる。ただし、固定順序で使用すれば必ず勝てる手順ではない。

スモークは味方の反撃やフラッシュの作用も妨げ得る。リコンは実際に対象を検知できる着弾・範囲・時刻で使う。フラッシュの効果中に射線を作れず、保持者が集合待ちを続ければ、使用しても利益を得られない。能力種別ごとの仕様を共有し、各役割の移動・向き・射撃・設置と時間を合わせる。

使用要求、エンジンの受理、実際の残数減少、着弾、観測可能な効果、事後に確認した敵への効果は別々に記録する。発射しただけで成功・安全を確定しない。事後の敵への作用は診断ラベルであり、推論時に非公開のblind値を読む根拠にしない。

### 4.3 公開根拠で有効な攻撃時間を見積もる

今回の所有FLASHの確認は、味方の公開チャージ減少と公開の飛行・着弾情報を用いた。新しい公開敵位置、壁、着弾時の煙、効果開始・終了を確認する。着弾時に煙で遮られた敵を、後から煙が消えたことだけでblindと扱わない。

攻撃可能時間に、移動＋設置／解除の残作業＋更新順に必要な余裕が収まるかを計算する。効果終了時刻がexclusiveなら、そのtickまで有効と誤解しない。

フラッシュ後も往復制限や集合待ちで前進できない問題に対し、確認済み効果が選択経路の既知射線をすべて覆い、期限内に作業できる場合だけ、該当制限や待ち目標を解放した。エンジンの禁止・味方予約・通路条件は維持し、移動や設置はモデルが選ぶ。未知の敵まで無力化されたとは扱わない。

## 5. 支援役、保持者・解除役、退避者を整合させる

### 5.1 近くにいるだけでは支援にならない

支援は同じ敵への射線、味方の向き・blind、壁・煙・身体遮蔽を確認する。別の敵を見ている味方や、壁に射線を遮られた味方を、保持者への支援人数へ単純加算しない。

入口内の支援役が目標10,42で止まっていても、公開敵7,38へは壁で撃てず、保持者だけが前進・退避を繰り返した例がある。教師にも、到着後に別の射撃位置へ移る例が必要だった。

支援位置は、到達可能、空いている、同じ敵を撃てる、保持者の設置目標を塞がないことを確認する。現在機能している支援を不要に動かさない。対象の失効、サイト・保持者変更、設置／解除開始などで支援計画を見直す。

### 5.2 目標到着で停止し続ける詰まりを調べる

保持者の目的地を味方が占有し、その味方自身も別の味方に通路を塞がれて動けず、静的最短距離だけを見る教師が停止する循環があった。

静的な距離、現在の占有を避けるtraffic距離、許された迂回長、各役割の最終目標を比較する。空き目標への限定的な変更で譲れるかを確認する。味方を押しのける不正な移動や、エンジンmaskの解除で解決しない。

### 5.3 退避先は予約と占有の両方で塞がれる

保持者を先に計画し、退避に必要な床を予約すると、後で計画する低HP役の退避が消える。翌tickには保持者の実占有で逃げられなくなることも確認した。

予約前の教師、予約後の教師、予約者、候補のmask理由を残す。退避指示が除外された場合、代替教師を設置目標への距離だけで選ぶと、敵側への前進へ変わる。今回のv19では、公開被射線・反撃不能射線・元の退避先への距離・向きを使い、退避意図を維持する代替教師へ修正した。

予約順を退避者優先へ変えた一手比較では、モデル自身が退避を選べた。しかし最終人数は改善せず、設置が遅くなった例もある。この変更は通常処理へ採用していない。局所の通行改善を、ラウンド全体の改善と扱わない。

## 6. 往復、待機、期限、行動計画の消失を調べる

### 6.1 支援待ち終了と、再進入・退避の矛盾

一定時間の支援待ち終了後に教師が前進を指示し、出ると支援不足のため退避を指示する組合せで、同じ危険入口を反復した。往復防止の辺通過制限が前進をmaskし、その後の待機も増えた。

前進を許す根拠、退避する根拠、次に再進入できる条件、支援・投擲・別入口・別サイトの可能性を整合させる。制限を全面解除して突撃させたり、無条件で安全位置に止めたりする修正は、死亡または時間切れを増やし得る。

### 6.2 移動したことを、任務の進捗と決めつけない

位置変更や交戦待ちで進捗時計を更新すると、入口の出入りが進捗扱いになる。逆に最寄り設置床の距離短縮だけを進捗にすると、正当な安全迂回・支援・情報取得を停滞と誤判定する。

選択経路、入口、作業進捗、敵への作用、待機理由を記録し、進捗定義を調べる。今回、停止検出を変えただけでは設置結果が改善しなかった。時計修正だけで解決としない。

### 6.3 全段階で同じ時間予算を使う

移動、集合、投射飛行、効果待ち、入口交戦、設置／解除の残時間を確認する。教師の迂回探索は間に合うと判断するのに、analysis候補は余裕不足で消える、といった不一致を防ぐ。

今回、移動＋設置4tick＋余裕5tickの条件で経路候補が空になると、設置可能な現在位置でも全員の行動計画が消えた。v18では通常候補と残存経路がすべて空の場合だけ余裕分を外し、実際の移動＋設置時間が残る候補を再生成した。モデルがPLANTを選ぶ余地を残す修正であり、設置を強制する処理ではない。

retakeでは、スパイク中心までの距離を単純に減算するのではなく、実際にDEFUSEが合法な範囲までの距離を計算する。guardは、解除阻止に間に合う射線・移動・投擲を確認する。作業可能床と所要tickはエンジン仕様を参照し、plantの数値を流用しない。

## 7. 教師、学習損失、報酬を目的と一致させる

### 7.1 教師は真理ではなく、比較対象である

モデルが教師と違うから誤りとは限らず、教師に従っても不適切な退避・再進入・無効投擲が起きる。教師100%、モデルのみ、同じ途中状態からの教師変更、一手だけの変更を区別する。

今回、モデルが作った失敗途中の状態では教師も再進入を反復したが、対象ラウンドを最初から教師で動かすと5v3設置できた。「局所状態での教師判断が悪い」と「教師全体も失敗する」は同じではない。

### 7.2 行動種類が合っていても、向き・対象が違えば失敗する

南へ動くことが教師と一致しても、東の敵に対して北西を向けば視認・射撃・後続の判断が変わる。FLASH役の一手で向きだけを変更すると、時間切れが4v3設置へ変わる比較を確認した。また、合法なFLASHを見送った一手を使用へ変えると4v4設置へ変わった。いずれも選んだ一例の反実仮想である。

種類別教師損失が、種類内の最大Q値を使うと、教師が示した向きではなく別の高いQ値へ正の勾配が入る。Touyama v3のv19学習では、教師種類のスコアを教師の正確な行動indexの値へ変更した。移動候補の8個は向き、ABILITYの8個は対象候補であり、同じ「8個」でも意味が違う。教師が最終maskで合法かも検証する。

損失値や分類精度だけでなく、どの出力へ勾配が入るかを小さな値配列で検証する。教師の向き・対象自体が不正なら強い損失で悪化するため、教師候補の意味を先に確認する。報酬や損失のコードを直しても、既存の保存重みが自動で正しい行動を覚えることはない。

### 7.3 距離・支援・作業進捗の報酬に矛盾や反復利益を作らない

最寄りサイトへの距離報酬は、選択した安全経路の迂回と逆の方向を加点することがある。経路選択、目標、教師、距離場を照合し、項目ごとの値とQ値を調べる。この項があるだけで実際の選択原因と断定しない。

支援距離や設置／解除進捗の加点が、往復・開始と中断の反復で利益を生まないかテストする。割引potentialは同じ距離場と終端処理で整合させる。正当な支援・退避・攻撃準備を、単なる停止という理由だけで一律に減点しない。

### 7.4 時間切れの先延ばしを有利にしない

敗北終端の減点が割引で薄くなると、失敗を遅らせる価値が生じ得る。失敗時刻の異なる行動列で、割引後の終端成分を比較する。

今回のplantでは、生存者の時間切れ−10、その他失敗−6を基準とし、各役の記録行動数Nに応じてGAMMA^(N−1)で割る補正を入れた。死者には自身の行動列に一般失敗を対応させ、生存者の後の待機や成功をそのまま後付けしない。

これは当該報酬の終端成分の整合性であり、全モデルへ同じ値・補正を採用する指示ではない。大きい即時罰の学習安定性、無理な突撃、退避・能力使用への影響を実評価する。報酬だけでは、maskで禁止された移動や消えた行動計画を直せない。

### 7.5 全設置へ正の完了報酬を与えつつ、品質を区別する

ユーザー方針は、1v5設置も完了として正の得点を持つが、人数有利の設置より価値を低くすること。人数不利設置の終端報酬をゼロ／負にする案は現在の方針ではない。死亡・被害などの途中減点は別なので、累積報酬が必ず正になるわけではない。

今回の式は、1＋8×味方人数/(味方人数＋敵人数)＋0.1×生存者の残り通常能力の味方割合。絶対生存数や5人生存・HP90%以上の特別加点で重複評価しない。設置前に敵を全滅させて実際に勝ったラウンドを「未設置だから失敗」と罰しない。

人数比は実際の勝率ではない。位置、HP、能力の種類、残り時間、guardの性能も関係する。設置後の勝ちやすさは最終的に実対戦で確認する。

## 8. analysisの予測対象と、実行モデルの依存を明記する

### 8.1 成功ラベルの意味を最初に定義する

| 予測対象 | 解釈できること | そのまま解釈できないこと |
| --- | --- | --- |
| どこかへ最終設置できるか | 別サイトへの変更を含む設置見込み | 現在選んだサイト・入口を突破できる確率 |
| 選択サイトで設置できるか | 同サイト内の適応を含む設置見込み | 特定経路・入口を維持した突破確率 |
| 指定入口の突破 | 定義した入口・観測・期限での突破 | その後の設置やguard勝利 |
| 設置後の勝利 | ケース条件と実行方策の下でのラウンド勝利 | 条件が違う人数・配置・能力での勝利 |

旧analysisのany-site成功を、選んだ右サイトの成功として読んでいた問題を分離し、v4では選択サイトへの完了ラベルへ変更した。同サイト内の再計画は引き続き含む。別入口へ変更した成功をすべて元入口の失敗へ書き換えると、適切な撤退・適応まで罰するので、予測したい対象から設計する。

### 8.2 結果を生成する実行モデルを固定・記録する

初回で実行モデルがないときはルール教師で始められる。plantなどが作成された後は、どの実行モデルの成績をanalysisが予測するかを明示し、そのモデルと元の依存ペアを固定して収集する。

収集中に新しいanalysis bestが保存されても、途中で固定plantの依存を入れ替えない。実行モデル・元analysis・hash・schema・相手・編成・探索・seed・ラウンド開始条件を保存し、再開時も同じ収集源を使う。不一致時に黙ってルール実行へ戻さない。

今回、analysis v4 set50の固定収集plantはv10 set30であり、後のv18/v19と同じ政策ではなかった。新plantを作ったから既存analysisもその実力を予測する、とは言えない。新しい実行モデルを固定した収集・再評価が必要になるが、その差だけが予測誤差の全原因だと断定しない。

### 8.3 予測精度と、選択した後の実力を両方評価する

全体Brier、入口別、公開接触後、90%以上などの高信頼群、実績成功率、対応できたラウンド数を記録する。50%固定のBrier=0.25などの比較も使う。ただし、予測誤差を最優先すると実際の設置・生存が下がる例もあり、精度指標だけでbestを入れ替えない。

学習replayへの適合を独立評価と呼ばない。長いラウンドの多数フレームを独立した多数試合として数えず、入口の較正などは定義した判断を1ラウンド1件にする。欠測を成功率0や良好な較正で埋めない。

analysisの右10/11は、保存された固定旧plantと評価条件で再現できた。11件はすべて偶数ラウンド・右2人配置で、最初の公開接触時に高信頼と予測された条件付き群だった。右全体、新plant、右3人への初期予測を表す数値ではない。「あり得ない数値」として削除するのでなく、実行役・seed・集計対象を照合する。

## 9. ラウンド番号と、段階をまたぐ実状態を扱う

相手AIがラウンド奇偶や通算番号で2:3 / 3:2、個別役割・anchorを変える場合がある。単一初回だけの収集ではなく、配置規則の違うラウンドと開始条件を含める。

旧12個のround one-hotが13以降すべて0になる問題に対し、analysis v4は12周期に加えて通算番号の入力を持つ仕様へ変更した。1～12と13～24のブロックも収集・評価する。これは実際の前半守備から後半攻撃への交代や延長戦を完全再現することとは別である。

search→retake、plant→guardでは、人数・HP・能力残数・位置・向き・blind/reveal・進捗・公開記憶・残り時間を引き継ぐ。相手の履歴やゲームの更新順も保持する。容易な初期化済みケースだけで後続モデルの性能を評価しない。

guard／retakeケースを作る上流モデルが変われば、ケースの分布も変わる。入力次元が同じだから以前のケースを無条件に再利用できる、と判断しない。依存hashとケース生成条件を確認して、再収集・再学習が必要な範囲を説明する。

## 10. 診断ログと、再現できる比較の作り方

### 10.1 行動前の公開情報と、行動後の採点を分離する

行動前のsnapshotと判断を固定してから、実エンジンの非公開状態を事後の死因・作用・報酬ラベルに使う。真の敵位置、敵の向き・blind・残能力などを、公開仕様にないままモデルや教師へ渡さない。

「未視認から撃たれた」「向きの外から撃たれた」「支援なし」「移動中死亡」は重複する監査ラベルで、単独では原因の証明にならない。射撃記録がない死亡も能力等を分けて調べる。

### 10.2 最低限残す判断情報

- モデル版・set・SHA、schema、scenario/LOS、依存モデルhash、収集実行役、編成、seed、開始ラウンド、教師・探索設定。
- tick、残時間、各役の位置・HP・向き・blind/reveal・能力残数・保持者／担当・作業進捗。
- 公開目撃、記憶の位置・年齢・情報源、幾何学的視界と確認済み不在、公開効果のphaseと期限。
- 候補経路・入口・距離・予測・点数内訳・除外理由、現在の目標、再評価理由・変更制限・進捗時計。
- エンジンmask、予約／辺通過／通路制限後mask、制限理由、除外前後の教師index・種類・向き・対象。
- 合法な上位Q、選択行動、同じ敵への支援、現在と候補移動後の射線、観測配列・maskのhash。
- 投擲要求・受理・残数変化・着弾・作用・期限、実移動・実分岐・実入口、設置／解除開始と中断、terminal結果。

ログを追加しただけの実行で、結果・判断・乱数状態が変わらないことを確認する。再encode・同tick二重更新・計画の作り直しで待機履歴や状態を変えない。NumPy座標をboolに変換した過去の出力不具合もあったため、型を検証し、壊れたログから位置を推定しない。

### 10.3 比較の種類を明示する

| 比較 | 主な用途 | 限界 |
| --- | --- | --- |
| 同一seedの全ラウンド | 実行方策全体の評価 | 行動後は履歴・乱数消費・ケース条件も変わる |
| 同一公開入力でモデルを比較 | 評価順位・Q・特徴量への反応 | 実際の対戦結果や因果効果ではない |
| 直前まで旧方策、対象だけ切替 | 同じ履歴から局所的に実行条件を比較 | 介入後の状態は変わる。全体の採用評価ではない |
| 一手だけの合法行動変更 | その判断から結果がどう分岐するか | 選んだ一例。通常モデルの実力とは異なる |
| 教師100% | 行動例の実行能力の確認 | 学習済みモデルの成績ではない |
| 仮想公開情報の入力 | 公開敵が増えた場合などの反応 | 実際の隠れた敵状態の再現とは限らない |

局所介入では、物理状態、公開状態、前ラウンド結果、Python/NumPy/Torchとコントローラの乱数、対象hashを照合する。対象を先に進めてから戻したことにせず、snapshotや保存経過から再現する。同じseedだけで同じ途中状態と主張しない。疲労・履歴を誤差の説明に使う場合も、その条件差と実測を示す。

## 11. 評価とbest選定は、勝つ目的に合わせる

通常モデルの実力は、教師・局所探索・経路探索なしで独立seedから評価する。モデル選定に繰り返し使ったseedと、最後まで未使用の検証seedを区別する。左右や入口別の母数が違う場合、率だけでなく件数も示す。

今回のplant bestは、全評価ラウンドに対して次の辞書式順で比較する。

1. 味方人数が敵より多い状態で設置した割合。
2. 同人数以上で設置した割合。
3. 同人数以上の設置で、生存味方の通常能力残数が敵より多い割合。

同点時のみ被害・設置時刻などを補助に使う。5人生存・HP90%以上は参考値であり主目的ではない。時間切れで人数を残しても成功へ加点しない。人数不利設置は全設置数・正の完了報酬には含むが、人数有利／同数以上の設置実績へは含めない。敵能力残数は評価ラベルとしてのみ取得し、欠測を0と扱わない。

このplant向け順位を、guardやretakeへそのまま流用しない。後続段階では実際のラウンド勝利・解除・解除阻止・期限・戦闘と配置の基本動作を評価する。plantの成功を試合の勝利と呼ばない。

## 12. 保存、互換性、良かった段階への復帰

best、latest、途中重み、評価済みcheckpoint、収集元、ログを区別する。set番号は新規実行で繰り返されるため、番号だけでモデルを特定しない。実行ID・モデルhash・版・相手・configを照合する。

schema変更には、観測・行動の構造だけでなく意味、教師、ラベル、LOS、scenario、依存モデルを含める。旧モデルは旧版の契約で読む。版・hashだけを書き換えて新モデルに見せたり、不一致を黙って無視したりしない。

報酬・教師・観測が変わるとき、重みだけを初期値として使える範囲と、optimizer/replayを継続できる範囲は異なる。許可した差分以外のschema・盤面・依存が一致することを検証する。元checkpointのバイト列・SHAを保ち、warm_startの由来、新しい学習回数、評価条件を記録する。

変更が悪化した場合は、コード、教師、報酬、重み、前ラウンドの履歴を分けて戻す。コードを全面的に戻す以外に、最新処理と良かった重みを組み合わせた診断で差を切り分けられる。ただし、重みをコピーした候補を新規版の学習済みモデルと呼ばない。

学習前と各セットの重みを、実行ごとのディレクトリに残す。未評価なら未評価と明記し、架空の評価値やbest資格を付けない。今回追加したreview_checkpointsは重みのみでoptimizer/replayを保存しないため、学習の完全再開用ではない。完全再開には別の検証済みlatest等が必要。

今回のv19 set1～4は後から復元できない。途中保存の追加は今後の実行にだけ適用する。保存されていない過去の重みを、評価値・replay・optimizerから復元したことにしない。

## 13. 新AI作成・改修時の実施順序

1. エンジンの観測・射線・更新順・作業合法範囲・能力・期限と、モデルの責務を確認する。
2. 教師、候補、目標、mask、報酬、成功ラベル、実行モデルの契約を設計する。接近・入口突破・作業・後続保持を分けてつなぐ。
3. 学習前に固定モデル／ルールで失敗を再現し、公開情報と事後ラベルの分離、ログによる挙動不変を確認する。
4. 一つずつ介入し、原因と局所効果を切り分ける。教師全体の対照も取り、不正な教師や候補欠落を先に直す。
5. 意味のある境界・回帰テストと、小さな実対戦比較を行う。右の改善と同時に左・他役割・期限が悪化していないかを見る。
6. 学習が必要な段階で、ユーザーに対象・初期値・変更点・再学習範囲・停止条件・評価方法を具体的に伝える。学習はこのプロジェクトではユーザーが実行する。
7. 少数対象で短く検証し、教師なしの実力で良い基準を超えるか確認してから広げる。長時間学習を、不具合診断の代わりにしない。
8. 新しい上流を採用した後、必要なguard／retakeケース・依存モデルを再収集・再学習し、実際の段階接続とラウンド勝利を確認する。

通常設定はスクリプト冒頭の名前付き定数にまとめ、作業ディレクトリとオプションなしの実行方法を明記する。「5セットで確認」なら総数上限と停止条件も一致させる。CLIだけの常用設定や、説明した回数を超えて動く設定を残さない。

再学習範囲は変更の依存で決める。analysis仕様が変われば、それに依存するplantや収集ケースも整合させる。plantの変更だけを理由に無関係なdefenderをすべて再学習しない。共有LOS・scenario・配置の変更なら、両陣営の影響を個別に確認する。

保存best v16 set10の独立72ラウンドは設置59、人数有利45、人数不利8、左33/34、右26/38、時間切れ11。後のv19 set5は設置60、人数有利37、人数不利12、左34/34、右26/38、時間切れ9で、bestを上回らなかった。左の良い判断を壊していないかを、右の改善と別に見る必要がある。

同じ前7ラウンド・開始時乱数・v19実行処理で右8ラウンドだけ比較すると、旧v16重みは69tick・5v2設置、新v19重みは59tick・4v2設置だった。旧処理のv16では5v2のまま時間切れ。この一例は、良い重みと処理修正を分けて評価する有益さを示すが、全面採用の評価ではない。

2026-10-12時点で、危険サイトの自律選択、右の時間切れ、人数有利での設置、左の良い判断の保持をすべて両立したとは判断していない。search / retake / guardへの共通概念は引き継ぐが、各モデルでの実力確認を省略しない。
