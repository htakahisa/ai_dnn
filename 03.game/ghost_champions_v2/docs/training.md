以前のFRC戦では設置前の時間切れが101/181ラウンドあった。

索敵役が死亡したりリコンを使い切ったりすると、残った索敵役の担当と護衛の組み合わせが変わっていた。
担当をラウンド内で固定し、FRCのB側2発目を `(9,29)` から投げる設定にした。
実際の着弾 `(6,40)` が、上側と下側のサイト通路を両方覆うことを実エンジンで検査した。

キャラクター設定等の編集が評価へ混入しないよう、ゲーム定義6ファイルを
`../data/runtime_fixed_20261007/` にコピーして比較に使用した。元のファイルは変更しない。
シード、対戦相手、BO3×10、チーム順序の交互切り替えも揃えた。

## OMGの設置後と公開解除情報の修正

前回の正式評価では、OMGの設置後勝利は93/237 (39.2%)で、40%の基準に届いていない。
`../tools/analyze_postplant.py` で保存済みリプレイを分析したところ、
全滅後の解除負け83件、生存者がいる状態での解除負け55件、その他の敗北6件だった。
生存者がいる解除負けのうち36件では解除完了時にスパイクが煙に覆われていた。
ログだけでは煙の所有者や敗因を断定できない。分析結果は `../logs/omg_postplant_diagnosis.json`。

補正モデルのフラッシュ候補で、解除進捗0の辞書も「解除中」と判定し、
設置後の照準をスパイク方向へ寄せる不具合を修正した。
進捗が正の公開解除通知がある場合だけ解除妨害の候補を作り、通常は知覚済みの敵を狙う。
解除中の人数・最大進捗と、自分の向き・被フラッシュ・感電・直前の移動・シールドを観測に追加した。
未観測の敵の座標や状態は入力しない。

入力が変わるため観測スキーマをv2へ更新した。旧434要素の教師データ・checkpointは再利用せず、
448要素で再収集・再学習する。この修正後の勝率はまだ正式評価していない。

## T6の学習構成

既存v1の重みは読み取り専用で使い、v2の規則が提案した行動を補正する小さな攻撃側モデルを新規学習する。
これは既存Carry等のDQNを直接更新する方式ではない。
防衛側factoryは既存 `GhostChampionsV1DefenderController` のまま。
対戦相手6チームにもoptimizerを持たせず、学習ラウンドの前後で重みのハッシュが一致することを検査する。
ゲームや相手controllerのソース・モデル・設定のハッシュも実行manifestに保存し、変更時は停止する。

観測スキーマv2は448要素。相手識別8、観測人数6、調査済み軸3、スパイク状態8、
自身・生存数8、アビリティ7、規則の提案10、周辺地形49、味方・知覚済み敵70、
公開解除情報2、自身の状態12、相手ロスター265を含む。
敵の座標・HPは知覚済みの場合だけ入力する。観測と行動のスキーマが異なるcheckpointはロード時に拒否する。

行動は21種類。規則の移動・待機・アビリティ・設置等を採用する4種類、上下左右、
8方向への照準、A/Mid/Bへのリコン、フラッシュ、回復。
壁・占有・設置後leash・FRCの未確定サイトへの進入をマスクする。
設置動作中とTYGでは規則の提案だけを許可する。
スモーク等も規則のアビリティ提案の採用として学習し、解除を隠す新規スモーク行動は追加しない。

実ゲームから各相手の教師ラウンドを再収集してBCを学習し、その後PPOで補正モデルだけを更新する。
BCの検証データはラウンド単位で分離する。
教師ラベルは「今回の規則提案を採用」であるため、BC正解率は勝率や能力向上の証明にならない。

PFSPは相手勝率 `p` に対して `(1-p)^2` に比例する。
勝敗報酬に `gamma * phi(next) - phi(now)` を加え、終端の潜在値は0にする。
`phi = 0.15 * (攻撃生存数 - 防衛生存数) + 0.2 * 設置済み`。
誘導係数は30万の判断数で0まで減衰する。潜在差がラウンド内で相殺されるよう、係数はラウンド間で更新する。
判断数は攻撃側キャラクターの行動決定回数を合計した値。
リコンの報酬は、実際に爆発した味方リコンで初めて判明した敵だけに付ける。
既に見た敵と重複する索敵、リコンの使用要求だけには報酬を付けない。
アビリティのBC損失係数には0.3の床を残す。

本学習はBC直後・5万判断ごと・終了時に6チームそれぞれBO3×10で評価する。
初期設定は35万判断で、最後の5万判断は潜在差とリコンの誘導報酬を0にする。
各相手100攻撃ラウンド未満なら検証不足として停止し、TYG勝率が80%未満なら回帰として停止する。
`last_passed_guardrail.pt` の `verified` はこの停止条件の通過を示し、全目標の達成を意味しない。
新しいcheckpointは自動的に対戦画面の標準モデルへ切り替えない。

## 実行方法

作業ディレクトリは `D:\git\ai_dnn\03.game\ghost_champions_v2`。

```powershell
Set-Location D:\git\ai_dnn\03.game\ghost_champions_v2
py training_attacker.py --run attacker_rl_defuse_20261007 --evaluation-workers 1
```

モデル・模倣データ・実行manifestは `data/<run>/`、学習ログ・評価リプレイは `logs/<run>/`。
同じ設定・ソースで中断した実行は `--resume` で再開する。
`--phase collect` は再収集まで、`--phase bc` はBCまで。`--phase rl` では存在する同じ実行のBCを使う。
同じrun名を再利用する場合も `--resume` が必要。設定・スキーマ・固定入力が変わったら新しいrun名で再収集する。
`logs/<run>/status.json` に段階・PID・更新時刻・教師収集数・BCのepoch・PPOの判断数を保存する。
再開時に定期評価が未完了なら、次の学習ラウンドより先にそのcheckpointを評価する。

短い動作検証:

```powershell
py training_attacker.py --run rl_check --verification --bc-epochs 2 --evaluation-workers 1
```

`--verification` は相手ごと2教師ラウンド、最大2,000判断、各相手BO3×1。
短い動作検証は100ラウンド条件や勝率目標の受け入れに使わず、verifiedモデルを生成しない。
ラウンド終了まで更新するため判断数は指定上限を少し超える。

明示的にモデルを使用する評価は、作業ディレクトリを `03.game` に移して実行する。

```powershell
Set-Location D:\git\ai_dnn\03.game
$env:GC_V2_RL_CHECKPOINT = (Resolve-Path ghost_champions_v2/data/attacker_rl_defuse_20261007/last_passed_guardrail.pt).Path
py tools/run_eval.py --controller v2 --series-count 10 --workers 2 --runtime-snapshot ghost_champions_v2/data/runtime_fixed_20261007 --output ghost_champions_v2/logs/rl_manual_evaluation
Remove-Item Env:GC_V2_RL_CHECKPOINT
```

## 実行状況

`rl_verification_20261007` は2回目のPPO更新で、相手のゲーム参照を通じて学習対象まで凍結する問題が発生した診断用の実行。
ゲーム本体と学習対象を探索から除外し、連続したFRC・GGラウンドでも学習対象が更新可能なことを回帰テストに追加した。
`rl_verification_fixed_20261007` でデータ再収集から動作確認をやり直した。結果は同名の `logs/` 内 `status.json` と評価フォルダに保存する。
最初の短い試行や途中のPPO勝敗を、受け入れ基準の達成とは扱わない。

PPOを7ラウンド・2,258判断実行した。6チームとのBO3×1も完了した。
各相手100攻撃ラウンド未満のため `milestone_sample_complete=false`、checkpointも `verified=false`。

BCを8epoch、その後6チームそれぞれBO3×10の初期評価を行う。

教師収集120ラウンド・42,487判断とBCの8epochは完了済み。
初期評価だけを継続し、完了後もPPOは実行しない。
評価条件を満たしたら `status.json` を `ready_for_rl` にし、実行コマンドだけを保存・表示する。
