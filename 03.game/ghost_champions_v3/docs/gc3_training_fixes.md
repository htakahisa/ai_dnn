# GC v3の学習経路の修正

## アビリティの合法性

FLASH/RECONはゲーム本体の延長Bresenham投射経路と同じ最初の一歩を判定します。最初から壁に当たって発射できない対象を確率分布から除外します。途中の壁に当たる投射は合法のままです。対象を別の位置へ強制的に置き換えたり、アビリティ使用を優先させたりはしません。

通常アビリティとNEON/ESCAPEの対象マスクを分離しました。FLASHが発射できない方向でも、合法なNEONは選べます。ESCAPEは既知の占有マスを除外します。未知の敵による占有など、観測できない原因でエンジンが行動を拒否する可能性は残ります。

## 入力層

大きな盤面入力と、小さな状況・キャラクター入力を別の枝へ通します。各枝と結合層にLayerNormを設け、TanhをSiLUに変更しました。定数の多い盤面が変化する情報を埋もれさせる問題と、Tanhの飽和による勾配の減衰へ対処しています。

新規方策はランダムな重みから作成します。旧構造のモデルは描画・比較時だけ明示的な互換読み込みを許可します。旧モデルを新構造へ移植したり、旧runを新しいコードで再開したりはしません。

## ポストプラント開始状態

設置時点で攻撃側が全員死亡している場合も、ゲーム本体は解除または爆発まで進みます。この場面ではGCが行動できないため、PPO行動データが0件になります。結果は評価・エピソードログに残し、学習時だけ `training_skipped=true` と `training_skip_reason=no_alive_attacker_at_phase_start` を記録して次のseedへ進みます。ダミー行動・報酬・stepは追加しません。行動可能な場面で記録が空になる異常は拒否し、0件の場面が24回連続した場合も停止します。

この修正は既存のモデル構造・報酬・配置マップ・重みを変更しません。修正前後の完全なソース指紋の組だけを `tools/gc3_training_compat.py` で許可し、ユーザーが再開した時点でmanifestに変更履歴を記録します。その他のソース・マップ・報酬変更に対する再開拒否は維持します。保存済みのPPO optimizer状態とstepを引き継いで再開でき、再学習は不要です。

開始時に10人を盤面全体へランダムに並べる処理を廃止しました。GCの選手構成で既存AIを固定して通常の試合を進め、実際に設置された時点で攻撃側の操作をGCの方策に交代します。位置・生死・HP・アビリティ残数・設置場所・設置前に発生した効果・残り時間・チームの知覚状態は引き継ぎます。防衛側は同じコントローラーをそのまま使います。

開始状態の生成元は学習スクリプト冒頭の `POSTPLANT_ENTRY_ATTACKER_CODES` で指定するTYG/OMG/FRC/FNC/SPSです。GGの攻撃AIはGorigonsの選手構成を要求するため、GCの開始状態生成には使いません。設置後の対戦相手は従来どおりTYG/OMG/FRC/FNC/GG/SPSの6種類です。

生成元はseedから開始順を決め、設置できなかった試合では次の生成元・別seedを試します。`POSTPLANT_ENTRY_MAX_ATTEMPTS = 24` 回で取得できなければ明示的に終了し、架空の配置で置き換えません。成功した設置状態だけを使うため、開始状態の分布は生成元AIの行動に依存します。GC自身の設置前方策との一致を保証するものではありません。

設置前の行動・勝敗はGCのPPOデータや学習stepに含めません。生成元の重み更新・GCへの重み継承・行動ラベルへの模倣学習はありません。候補マップの編集、候補への固定配置、決定論的な行動選択も行いません。

`episodes.jsonl` の `phase_start` に生成元・実際のseed・試行回数・設置時のキャラクター状態を保存します。

## 通常の実行

設定場所は `gc3_train_attacker_guard.py` / `gc3_train_defender_search.py` 冒頭です。保存先は `attacker_postplant_fixed_v1` / `defender_search_fixed_v1` です。攻撃側は中断した4,363 stepから再開する `RESUME = True`、現在の実行指定に合わせた `TRAINING_STEPS = 80066` です。防衛側は新規学習の `RESUME = False`、`TRAINING_STEPS = 20000` に設定しています。過去のモデル・ログは保持しています。こちらから学習は起動していません。

作業ディレクトリは `D:\git\ai_dnn\03.game\ghost_champions_v3` です。

```powershell
Set-Location D:\git\ai_dnn\03.game\ghost_champions_v3
python gc3_train_attacker_guard.py
```

防衛の新規学習は同じディレクトリで `python gc3_train_defender_search.py` を実行します。

攻撃側も新しく1から始める場合は、`RUN_NAME` を未使用の名前に変更し、`RESUME = False` にします。継続する場合の `TRAINING_STEPS` は追加分ではなく累計の到達stepです。

ゲームは修正後の保存先を優先します。まだ修正後のモデルがなければ、保持した報酬変更後の攻撃モデル・旧防衛モデルを描画用に読みます。グラフは修正後のrunを初期表示し、以前のrunも選べます。既に開いているモニターは再起動が必要です。

## 検証

GG戦での `retake checkpoint mismatch: scenario_signature` は、GCの選手構成を動かす設置前の補助AIの名前だけでGGが専用モデルを選んだことが原因でした。ConCon側はAI名と公開された選手構成の両方を確認するように修正しました。名前と構成が一致しない場合は通常の共通モデルを使います。マップ署名などのチェックポイント検証は維持しています。

停止したseed `20261045` のGG左サイトで、保存済みの4,363 stepの方策から動作を確認しました。モデルの更新は行っていません。記録は `logs/validation/gc3_gg_runtime_fix.json` です。途中でログだけに残った未更新の5試合分は `logs/attacker_postplant_fixed_v1/recovery/` に保存し、再開で二重に計上しないようにしました。今後の再開でも、保存済みチェックポイント以降のログを退避してから再収集します。

GCの47テストと、ConConのモデル選択に関する4テストが通っています。ConConの広いテストでは専用学習の保存回数の期待値に既存の不一致が1件あり、変更前の選択処理でも同じ失敗を確認しました。今回のモデル選択修正とは別の問題です。

投射対象をゲーム本体の判定と比較し、記録時とPPO再計算時の確率一致、新構造の状態入力への勾配、互換読み込み、設置後の状態保持をテストしています。検証でoptimizerの更新は行っていません。実際の設置から6種類の相手に対する行動収集を確認した記録は `logs/validation/gc3_training_fixes_postplant.json` にあります。これは学習成果の評価ではありません。
