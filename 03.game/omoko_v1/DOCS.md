# 各phase での重要な戦略について

## retake
- 敵を全員倒した後は敵の位置情報などはすべてクリアし、またスパイクの位置にBFS距離で最短で進みスパイクを解除する。敵情報が残っていると敵を全員倒したにもかかわらず警戒して移動しないことがあるため。
- フラッシュアビリティを使った後は積極的に進み、敵を倒していく。ただし、敵の隣は弾が当たりやすく、フラッシュを食らっている相手でもかなり危険なため、1マス以上空けてフラッシュを食らっている敵がいたら止まって射撃し、倒してまたどんどん進んでいく。特に先頭のキャラは後ろが使えるので前に進むこと。
- 敵がスパイクの解除を行った場合は情報としてわかるようになっている。スモークに隠れて解除されるとスパイクまで近づかないと敵への射線が通らずスパイク解除を許してしまうので、スモークに隠れて解除している敵を見つけた瞬間にスパイクの方に移動し敵を攻撃する必要がある。
- スモークやフラッシュは同じ場所に焚いても意味がないので、マップ上複数の定点がある場合は近いところにすでに味方が撃っているのであれば、次はその先のポイントに向けて撃つ必要がある。少なくとも味方がそのポイントの先にいる場合は手前はクリア済なのでアビリティ使用はあまり意味がないため。

## search
- 初期配置経路（`uppercase_setup_frontier_queue_v2`）: 移動中の味方が通路を塞いでいる場合は、3tick相当の待機コストと迂回距離を比較し、短い待機で済む経路ではその場で待つ。移動中の味方のマスへは進入せず、配置済みの味方は通常の障害物として迂回する。Setupと通常searchで学習・推論共通の処理を使い、配置地点・マップ・射線判定・観測/行動の形式は変更しない。既存モデルは読み込めるが、初期配置中の行動分布が改善前と変わるためsearchの追加学習・評価を推奨する。他フェーズの再学習は不要。待機コストは `ov1_defender_search_routes.py` 冒頭の `DEPLOYMENT_TRANSIT_WAIT_COST` で調整する。
- 中央オーブ回収（`quiet_team_outing_flash_priority_v2`）: 初期配置を完了し、敵の視認・共有目撃情報・スパイク情報がない状態が8tick続いていれば、生存メンバー全員で中央オーブへ向かう。回収役1人は、ウルト未満かつ到達可能なフラッシュ持ちを最優先し、その中でウルトの不足ポイント、オーブまでのBFS距離、名前の順に決める。対象のフラッシュ持ちがいなければ他のキャラから同じ順で選ぶ。他のメンバーは別々の周辺マスで外側の通路を警戒する。
- 回収は通常戦闘より低優先度。移動中・回収中・帰還中のどの段階でも、敵情報・スパイク情報があれば回収/帰還の指示を停止し、従来の戦闘・支援処理を使う。回収成功後、または回収役死亡・40tick経過・残り20tick未満の場合は、敵情報がない間に元の担当位置へ戻る。出発は1ラウンド1回とし、全員ウルト最大・中央オーブ取得済みの場合は出発しない。
- 回収・護衛・帰還の経路は学習側と推論側で共有する。担当位置そのものは変更しない。オーブ行動中に元の担当位置から離れるペナルティを与えず、回収成功の報酬はsearch用定数で0.02に抑える。
- 設定は `ov1_defender_search_orb.py` 冒頭の `IDLE_ORB_*` 定数、回収報酬は `ov1_train_defender_search.py` の `IDLE_ORB_COMPLETION_REWARD` で変更する。観測84次元・行動96通りの形式、マップ、壁の射線判定は変わらないため、既存searchモデルは読み込める。行動分布と報酬が変わるため、新ルールに合わせた追加学習・評価を推奨する。他フェーズのモデルの再学習はこの変更のためには不要。実行中のPythonには反映されないため、新ルールで学習する場合はスクリプトを再起動する。
- 作業ディレクトリ：`03.game/omoko_v1/`（移動済み）。通常実行は `python ov1_train_defender_search.py`。学習回数等は同ファイル冒頭の名前付き定数で設定する。
- スモークはリテイクに重要なため、最初の指定tick (例 30 tick)はスモークの使用を禁止するなどの工夫が必要
- 敵を待ち構える phase のため、無意味に移動して射撃せずに、指定された警戒ポイントをきちんと警戒することが重要。ただし、別の場所から敵に撃たれたにもかかわらず反対の警戒ポイントをfacingするように上書きしていることがあった。敵を待ち受けて倒すという行動を全く理解していない行動であり問題である。第一目標として敵の方向を向くという大前提を無視して警戒ポイントをむく、という単純な不具合修正をしたことを恥ずべきである。敵がいるのが分かっているのであれば敵の方向を向くのは当たり前で、敵がいる場所がわからないために警戒ポイントを見ているという単純明快な話を理解しない行動は許容しない。

## carry
- carryは `ov1_learning_attacker_carry.py` 冒頭の `ROUTE_PRIOR_ENABLED`・`ROUTE_PRIOR_MIX = 0.5`・`ROUTE_PRIOR_SUMMARY_PATH` で事前勝率の利用を設定する。軽量サマリJSONはコントローラー初期化時に一度だけ読み、最初の6ラウンドは相手AI・編成が一致するデータから、正規化した勝率50%＋全候補均等確率50%で抽選する。7ラウンド以降は従来の試合内成績に基づく85%活用＋15%探索のまま。サマリなし・モデル/地形不一致・未評価の相手/別編成の場合は従来の使用回数をそろえる初期探索へ戻る。
- 軽量サマリはデータ収集完了後に `ov1_summarize_attacker_carry_routes.py` を一度実行して作成する。作業ディレクトリ：`03.game/omoko_v1/`（移動済み）、通常コマンド：`python ov1_summarize_attacker_carry_routes.py`。入力/出力/表の保存先は冒頭の `INPUT_PATH`・`OUTPUT_PATH`・`TABLE_PATH`。未完了データは出力せず、完了した集約JSONから `data/carry_route_evaluation/route_priors_summary.json` と `route_win_rates_summary.md` を作る。carryは詳細な対戦JSONを読まず、ラウンド/tickごとのファイルアクセスも行わない。更新は次にコントローラーを生成したときに反映する。
- 事前成績のキーは相手AI＋サイト＋中継点の座標。床上の中継点追加では既存経路のデータを保持し、未評価経路には既存経路の平均強度を補って均等確率相当の初期確率を与える。削除経路は候補から除く。壁・サイト/優先設置場所・モデルが変わった場合は再評価する。今回の変更は経路抽選のみで、観測/行動の次元・射線判定・モデル重みは変更せず、再学習は不要。収集中の経路固定評価では抽選メソッド自体を上書きするため今回の追加の影響を受けず、既存収集結果からの再開互換も維持する。
- 評価の通常実行は `PARALLEL_WORKERS = 6` により相手AIごとの6プロセス並列。Windowsのspawn方式で、CWD・乱数・CPU推論・モデルキャッシュをプロセスごとに分離する。12ラウンドセットの途中を分割せず、同じseedなら逐次実行と同じセットを評価する。`--workers 1` は一時的な逐次実行、`--workers N` は並列数の上書き。
- 並列時の途中データは `data/carry_route_evaluation/route_win_rates_12round_sets_workers/<AIキー>.json`、詳細ログは `logs/ov1_evaluate_attacker_carry_routes_<AIキー>.log`。集約JSONは親プロセスだけが書き込み、完了済みセットを定期的に反映する。再開時はAI別JSONの最新結果を読み、集約済みの結果だけがある場合はそこからAI別ファイルを作る。最初からやり直す場合は `OUTPUT_PATH` を別名にする（集約JSONだけを削除しても、対応するAI別JSONが残っていれば再開する）。
- Windowsで親の読み取りと子のファイル置換が重なった場合は短時間のリトライで保存する。ゲーム/AI・マップ・モデル・seed・評価プロトコルが一致する場合に限り、評価器自身の保存/並列処理の変更後も元の識別情報を履歴に残して再開できる。評価条件や対戦方法を変える実装では `EVALUATION_VERSION` を必ず更新する。
- 相手別・経路別の事前勝率データ作成は `ov1_evaluate_attacker_carry_routes.py`。通常設定は冒頭の `ROUNDS_PER_SET = 12`、`SETS_PER_ROUTE = 8`（各AI・経路で計96ラウンド）、`OPPONENTS`（Toru AI v4 / ConCon v1 / Touyama Gaming v3 / Fnatic v3 / FRC v1 / Ghost Champions v2）、`BASE_SEED`、`OUTPUT_PATH`、`RESUME`。旧AI・同AI対戦は対象外。相手の編成も `OPPONENTS` で指定するため、AI名と編成をセットで比較する。
- 評価の作業ディレクトリ：`03.game/omoko_v1/`（移動済み）。通常実行コマンドは `python ov1_evaluate_attacker_carry_routes.py`。`--check` は対戦しないマップ候補・再開情報チェック。`--sets` または `--rounds`（12の倍数）、`--opponents`、`--output` は一時検証用の上書き。既存AIの相対モデルパスは評価アダプター内で解決し、呼び出し元の作業ディレクトリは復元する。出力先は絶対パスでこのAI配下に固定する。
- 現在は右3・左3の6経路なので、本評価は6AI×6経路×96＝3,456ラウンド（288セット）。経路は現在のcarryマップから毎起動列挙し、保存キーは `site:row,col` として番号のずれを防ぐ。各セットでゲームとコントローラーを新規作成し、同じゲーム・同じコントローラーのまま攻守交代なしで攻撃側12ラウンドを連続実行する。ウルトポイント・得点・メンタル・相手AIの試合内情報を通常どおり持ち越し、ラウンドごとの再seedは行わない。12ラウンド中はOmokoの攻撃経路を同じ対象経路へ固定する。元のIQ視界・戦闘・設置・guard・retake・勝敗判定を使い、設置後も決着まで対戦する。観測やモデル重みは変更せず、学習は行わない。優先設置先は本番carryと同じチェックポイントのメタデータを使用し、実際の設置目標も記録する。
- 本評価データは `data/carry_route_evaluation/route_win_rates_12round_sets.json`、詳細ログは `logs/ov1_evaluate_attacker_carry_routes.log`。勝数・敗数・ラウンド数・勝率・設置回数に加え、セットごとのseed、ラウンド番号、得点、開始/終了時のウルトポイントを保存する。完了した12ラウンドセットごとに一時ファイルから置換して保存し、同じコマンドで未完了セットから再開する。途中セットは試合内情報を失ったまま途中再開せず、元のseedでセット先頭から再実行する。1ラウンド独立方式の旧データはschema/versionを分けて混在を拒否し、旧ファイルはそのまま残す。モデルが無い/不整合などの失敗は勝率0%にせずエラーとして保存し、他AIの評価を続け、最後に未完了を通知する。
- マップ・AI/エンジンソース・seedの識別情報と、読み込んだモデルのSHA256を記録する。モデルファイルの評価中の更新や、再開時のソース/モデル変更は結果混在を防ぐため拒否する。その場合は冒頭の `OUTPUT_PATH` を別名にして再評価する。評価完了後に軽量サマリを作成すると、次回起動のcarryで上記50%混合の初期抽選に利用する。
- 推論時の中継点はチェックポイント内の `waypoint_cells` ではなく、現在の `ov1_map_data_carry.py` のマップから読む。`6` は右、`7` は左の候補として、学習側と同じ行・列順ですべて列挙する。中継点数の上限を固定せず、追加・削除は次回起動時に反映する。優先設置マスのメタデータ、モデルの重み、最初の6ラウンドとその後の抽選ルールはこの読み込み変更では変更しない。
- 変更時点ではcarryのbest/latest両チェックポイントと現在のマップの中継点は一致（右2点・左2点）。読み込み元の変更だけなら再学習は不要。将来中継点を追加・移動すると進行経路と観測の分布が変わるため、carry・escortの動作評価を行い、必要に応じて追加学習する。観測/行動の次元と壁の射線判定は変更しない。
- 近くにオーブがあり、敵の脅威がなく(敵の目撃情報がない)、自身のウルトポイントがmax ではない場合はオーブを取得すること

## escort
- 学習中のcarryは `ov1_map_data_carry.py` の中継点（6=右・7=左）を経由して、同じサイトの優先設置マス（5、無い場合は2）へ進む。左右を等確率、そのサイトの中継点を等確率で選択する。中継点は隣接1マス以内で到達扱いとし、候補数はマップから自動取得する。escortマップの定点アビリティ情報は従来どおり使用する。
- 学習設定は `ov1_train_attacker_escort.py` 冒頭の `EPISODE_COUNT`、`BATCH_SIZE`、`LEARNING_RATE`、`EVAL_EVERY`、`EVAL_EPISODES`、`SEED` などの名前付き定数、保存先は `SAVE_DIR`。作業ディレクトリ：`03.game/omoko_v1/`（移動済み）。通常実行：`python ov1_train_attacker_escort.py`。既存重みを読み込まない新規学習。チェックポイントに `carry_route_version` と中継点・設置候補を記録する。
- 計算の高速化は冒頭の `BATCH_ACTION_INFERENCE = True`（同じtickの生存escortのうち、探索でランダム行動しない者をまとめて推論）と `CACHE_WALL_DISTANCE_MAPS = True`（carry・設置先・オーブを起点にした壁のみのBFSを再利用）。学習時も評価時も一括推論を使用する。報酬・観測・行動・射線判定・探索乱数の消費順・重み更新頻度・評価回数は変更しない。距離キャッシュは環境ごとに保持し、壁配置の変更時に破棄する。キャラ占有はキャッシュせず移動時に判定する。高速化のための再学習は不要で、既存モデルと保存形式は互換。
- 一括推論は浮動小数点の丸め差を生む場合がある。上位候補が僅差の場合は `BATCH_ARGMAX_TOLERANCE` を基準に従来の個別推論で再判定する。テスト範囲では行動・報酬・観測・乱数状態の一致を確認したが、学習完了時の重みのビット単位の一致は保証しない。個別推論を維持したい場合は `BATCH_ACTION_INFERENCE = False` とし、距離キャッシュだけ有効にできる。両方 `False` にすると従来の計算方式になる。
- 学習を開始しない回帰確認：作業ディレクトリ `03.game/omoko_v1/`（移動済み）で `python -m unittest discover -s test -p 'test_ov1_train_attacker_escort*.py'`。テストは重みを更新せずモデルも保存しない。
- この変更は学習中のcarry経路の変更で、観測・行動の次元や射線判定、既存モデルの読み込み形式は変えない。既存escortモデルは引き続き読み込めるが、新経路での護衛を学ばせるにはescortを再学習する。モデル更新後はcarryの事前勝率評価とサマリ生成もやり直す。
- 近くにオーブがあり、敵の脅威がなく(敵の目撃情報がない)、自身のウルトポイントがmax ではない場合はオーブを取得すること

## guard

- 解除通知（`defender_defuse_info` の進捗が正）を推論側の最優先処理にする。解除者が見えて射線が空いていれば停止してその方向を向き、自動射撃に任せる。解除者を撃てない間は、別の敵が見えていてもスパイクへ接近する。未視認の敵座標は参照せず、公開されている設置地点へ移動する。
- 接近には味方・視認できた敵の占有を考慮したBFSを使う。一時的にスパイクから離れる迂回も許可し、スパイクのマスを優先する。到達不能なら隣接する到達可能マスを目標にする。射撃はゲーム側の壁・スモーク・他キャラの遮蔽・強制向きなどの条件に従う。
- 解除中でも交戦中でもない場合は担当ガード地点まで移動する。古い共有目撃情報やモデルのウルト・オーブ選択で移動を中断しない。到着後は移動・ウルト・オーブを禁止して持ち場を維持し、向きと通常アビリティはモデルが選択する。敵を撃てる場合は停止して敵方向を向く。
- 推論のみの変更。観測・行動形式、配置、シナリオ識別値、壁の射線判定、モデルは変更しない。既存モデルを使用でき、この修正のための再学習は不要。学習スクリプトは実行しない。
- 回帰確認の作業ディレクトリ：`03.game/omoko_v1/`（移動済み）。`python -m unittest discover -s test -p test_ov1_learn_attacker_guard_priority.py`。

## 攻守共通の破壊エリア回避

- `ov1_inference_damage_avoidance.py` の `AVOID_DESTRUCTION_AREAS = True` で、carry・escort・retrieve・guard・search・retake 共通の推論側回避を有効にする。公開エフェクトのチーム視界に含まれる破壊エリア（ASH・BALEMOON）とBALEMOON予告マスを避ける。所有者や残り時間・未視認の範囲は参照しない。公開情報では敵味方の区別がないため、見える対象範囲をすべて危険扱いにする。
- 現在地が危険範囲なら、通常の移動・戦闘・設置・解除より退避を優先する。ただしattackerで解除者が今すぐ射撃可能な場合は、その場で解除阻止の射撃を優先する。範囲外なら危険マスへの予定移動を取り消し、進行方向の範囲外マスまで安全な道で迂回する。通行可能な経路がなければ範囲外で待つ。味方などの占有マスを避ける。視認前の着弾や逃げ道のない状況を完全に防ぐものではない。
- ASHは1行動1発・1ラウンド2発（`game_core.py` の `ASH_CHARGES_PER_ROUND`）。3×3の破壊エリアが10tick残り、踏むと5tickの命の契約が付く。通常は毎tick HPとHP上限が10ずつ減る（シールド等の軽減はゲーム本体に従う）。効果中の別マス・重複エリアでは加算も延長もしない。契約終了後も有効な範囲にいれば再付与される。範囲外へ出ても付与済みの契約は消えない。
- ゲーム本体・射線判定・マップ・シナリオ識別値・学習時の観測/行動形式・既存モデルは変更しない。推論の回避処理だけなので再学習は不要。経路選択が変わるため、過去のcarryルート事前評価は新しい推論で再評価する必要がある。
- 回帰確認の作業ディレクトリ：`03.game/omoko_v1/`（移動済み）。`python -m unittest discover -s test -p test_ov1_inference_damage_avoidance.py`。学習・モデル保存は行わない。

## 共有目撃情報に対する向きと解除阻止

- `ov1_inference_team_tactics.py` の `USE_SHARED_ENEMY_FACING = True` で攻守6フェーズの移動・待機時の向きを補正する。解除者、今の移動先から射撃可能な敵、それ以外の共有済みの敵の順で警戒する。壁越しの共有目撃も向きの選択には使う。アビリティ・ウルトの方向指定と被弾による強制向きは優先して維持する。
- `IQAwareController` に `requires_exact_team_tactics` を要求するomokoの攻守コントローラーだけ、チームに開示済みの敵・味方の座標と公開された設置位置を、向き合わせと解除阻止用の補助情報として受け取る。通常のモデル観測は従来のIQ補正のまま。未発見の敵は既存の `build_team_position_view` により `position_known=False`・座標 `(-1, -1)` のままで、補助処理の対象にしない。他チームへの既定の知覚処理は変えない。
- 解除中は補助情報の設置位置へ接近するため、IQで毎tickずれた設置位置を追い越さない。既知の解除者を撃てれば停止して向き直す。味方や壁に射線を塞がれた場合は最寄りの射撃可能位置へ移動する。解除者が未発見のまま設置地点へ到着した場合は、その場で90度ずつ向きを変えて視認を試み、同じ方向のまま待ち続けない。
- 射撃可能性の補助判定はゲーム本体と同じ `wall_line_cells`、隣接時のスモーク可視ルール、プレイヤー遮蔽を使う。ゲーム本体の射線仕様、配置、シナリオ識別値、モデルの観測・行動次元は変更しない。既存モデルで使用でき、再学習は不要。過去のルート勝率は推論動作が変わるため再評価が必要。
- 作業ディレクトリ：`03.game/omoko_v1/`（移動済み）。学習しない回帰確認：`python -m unittest discover -s test -p test_ov1_inference_team_tactics.py`。IQの入口・実際の射撃処理・解除完了判定を通し、命中を固定した条件で6tick以内に解除者を倒せることを確認する。任意の実戦で撃破や勝利を保証するテストではない。
