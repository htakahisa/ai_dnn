# 定点アドバイザーの不要なFLASH使用の調査（2026-10-17）

## 目的から再調査した結果

目的は、omoko_v1 が効果を見込めない定点で実際にアビリティを消費する回数を減らすことである。区分の合格数や最後の候補の正解率だけでは、この目的を評価できない。以下の追加調査は、以前の「閾値・検証条件を先に調整する」という優先順位を訂正する。

私は、`ov1_train_attacker_ability_advisor.py` の `load_samples()` が、同じ試合・ラウンド・区分について最後の1件だけを学習・検証・テストへ残していることを確認した。そのキーは時刻と使用者を含まず、時刻や使用者の異なる判断も上書きする。実行側は次の判断で同じ定点を再判定するため、学習・評価対象と実行時の判断機会が一致していない。

私は、診断スクリプトも同じ整理方法を使っていたため、前回の再推論ではこの問題を見落とした。私は、診断スクリプトに全候補の系列を確認する処理を追加した。

最大の残存セットにおける、教師が全時刻の候補を不要としたラウンドの集計は以下のとおりである。

| 区分 | 対象ラウンド数 | 最後の候補で使用許可が出たラウンド数 | 全候補のどこかで使用許可が出たラウンド数 |
| --- | ---: | ---: | ---: |
| (11,16) carry_L | 109 | 6 | 102 |
| (13,31) carry_R | 121 | 3 | 39 |
| (11,16) escort_L | 91 | 22 | 47 |
| (13,31) escort_R | 101 | 17 | 19 |

carry_R の (13,31) では、別の1ラウンドに必要・不要の両方のラベルがあるため、この表はそのラウンドを除外している。3セットのすべてで、carry_L の (11,16) について、最後の候補だけの評価と全候補の評価に大きな差があった。ただし、残存セットの互換性・出自についての限界は後述のとおりであり、この集計は実投擲回数ではない。

私は、修正の優先順位を次のように訂正する。

1. 学習処理は、時刻・使用者・入力状態が異なる候補を保持する必要がある。学習処理は、完全な重複の整理、ラウンド数の集計、ラウンドごとの重み付けを、状態の削除とは分けて扱う必要がある。
2. 評価処理は、最後の1件ではなく全判断機会を検査する必要がある。評価処理は、不要な候補への使用許可率に加え、全候補が不要だったラウンドで一度でも使用を許可した割合を報告する必要がある。
3. 学習処理は、適切に保持した検証データで、不要な使用許可の削減と必要な使用の維持を基準にモデル・閾値を選ぶ必要がある。テストデータは最終確認に使用する。
4. 対戦評価は、carry・escort 別の実投擲を記録し、教師上の必要性と実際の敵への効果を照合する必要がある。候補への助言数だけでは、対戦評価は不要な消費が減ったかを判定できない。

私は、不合格区分を増やすだけの変更や座標の固定禁止を、今回の解決策にはしない。既存の不合格時の全使用許可という動作を維持したまま検証条件だけを強化すると、既存の温存が取り消されるためである。検証指標を増やすこと自体は、モデルの行動を改善しない。

私は、今回、診断処理とこの調査記録だけを更新した。今回の再調査は学習処理・通常対戦の動作・重み・教師を変更していないため、ユーザーによる再収集・再学習は今回の診断を理由としては不要である。上記の学習データ保持方法を実際に修正した場合は、omoko_v1 の定点アドバイザーモデルの再学習が必要になる。現在は出自を検証できる完成済みデータが残っていないため、その再学習には現在の仕様に対応した完成済み収集データを用意する必要がある。

私は、omoko_v1 の保存済み定点アドバイザーモデルと残存収集データを読み取り、frc_v1 相手の (13,31)・(11,16) の使用許可を調査した。私は、学習、完成済みデータの読込関数（旧データを削除する処理を含む）、モデル変更、閾値変更を実行していない。

## 保存済みモデルから確定できる結果

通常対戦のコントローラーは、carry・escort の両方の定点候補をアドバイザーへ渡す。アドバイザーは、次の順序で定点を判定する。

1. アドバイザーは、公開された敵に対する効果の射線などの関与を確認すると使用を許可する。
2. アドバイザーは、未検証の区分について使用を許可する。
3. アドバイザーは、その他の検証済み区分について、モデルのスコアが0.10以上なら使用を許可する。

指定の主な4区分はすべて検証済みであり、保存済みモデルのテストレポートは以下の結果を保持している。

| 定点・区分 | テスト件数 | 教師が必要と判定した件数 | 判定処理が温存しない件数 |
| --- | ---: | ---: | ---: |
| (13,31) carry_R | 33 | 0 | 2 |
| (13,31) escort_R | 33 | 0 | 5 |
| (11,16) carry_L | 33 | 0 | 3 |
| (11,16) escort_L | 25 | 0 | 8 |

これらの件数は候補に対する判定であり、ゲーム中の実投擲回数を表さない。個々の対戦の使用理由を特定するには、その対戦の観測とアドバイザーの判定記録が必要になる。

## 残存データによる閾値の比較

私は、3セットの `.parts` を読み取り、学習スクリプトと同様に試合・ラウンド・区分が同じ行の最後の1件を採用して再推論した。現在のモデルは、現在の重み・シナリオに対する全4区分の互換性検査に合格した。

現在のデータディレクトリには完成済みJSONLがなく、`.parts` には互換性情報のヘッダーと完了マーカーがない。3セットの件数もモデルに保存された元の学習・検証・テスト件数と一致しない。そのため、私は以下の結果を、現在のモデルへの追加入力に対する診断として扱う。以下の結果は、元のテストの再現結果や独立した汎化性能の測定ではない。3セットは同じseedの試合を含むため、私は3セットの件数を合算しない。

最大セット `702d396fc72149d9a4b094d5f1869f80.parts` は、重複整理後16,624件を含む。

| 区分 | 教師が不要と判定した件数 | 0.10での使用許可 | 0.20での使用許可 | 0.50での使用許可 |
| --- | ---: | ---: | ---: | ---: |
| (13,31) carry_R | 122 | 3 | 1 | 0 |
| (13,31) escort_R | 101 | 17 | 5 | 0 |
| (11,16) carry_L | 109 | 6 | 2 | 2 |
| (11,16) escort_L | 91 | 22 | 8 | 0 |

この4区分では公開敵の関与による使用許可が0件であり、全使用許可がモデルのスコアによる。carry_L の (11,16) に対して、モデルは最大約0.758のスコアを出した。したがって、低い閾値とモデルの過大なスコアの両方が不要な使用許可に寄与している。

同セット全体で既存の検証済み区分を固定して閾値だけを0.10から0.20へ上げると、不要な使用許可は9,252件から8,886件へ減る一方、必要な候補3,241件に対する温存は19件から48件へ増える。この全体集計はFLASH以外と他の相手も含む。既存の検証合格条件は0.10で判定されているため、ユーザーはこの比較だけを根拠に0.20を採用できない。学習・評価処理は、変更後の閾値に対して区分ごとの合格条件を再評価する必要がある。

## 原因の切り分け

- 使用判定の設定：0.10という閾値は、0.10～0.20程度の低いスコアの候補にも使用を許可している。
- モデルの判別精度：モデルは、不要な候補の一部に0.50以上のスコアを出している。閾値を少し上げるだけでは、この誤判定は残る。
- 検証合格条件：`safe_group()` は、必要な候補を温存した割合と、温存した候補に必要な候補が混じる割合を制限している。同関数は、不要な候補のうち使用を許可した割合を制限しない。そのため、不要な使用許可が残る区分も検証に合格する。
- 学習回数不足：モデルは検証損失0.2640を保持するが、学習スクリプトはエポックごとの履歴、最良エポック、学習損失をモデルに保存していない。今回の調査では対応する学習ログも確認できなかった。私は、学習回数不足、過学習、共有モデルの表現力不足、データの偏りを今回の資料だけで区別できない。

私は、改善の第一候補を「不要な使用許可の割合も評価する検証」と「検証データによる閾値の選定」と考える。ユーザーが指定2座標を固定禁止する対応や学習回数だけを増やす対応を採用する前に、学習処理は、必要な候補の温存率と不要な候補の使用許可率を両方評価する必要がある。今回の調査は射線・観測・配置・既存モデルの重みを変更していないため、この調査による再学習は不要である。

## 再実行

ユーザーは、診断スクリプト冒頭の `DEFAULT_DATA_DIR`、`DEFAULT_THRESHOLDS`、`DEFAULT_OPPONENT`、`DEFAULT_POINTS`、`DEFAULT_OUTPUT` で診断対象を確認・変更できる。

作業ディレクトリ：`03.game/omoko_v1/`（ユーザーがこのディレクトリへ移動済みの状態）。ユーザーは通常、次のコマンドで診断を実行する。

```powershell
python ability_advisor_v1/ov1_review_attacker_advisor_scores.py
```

診断スクリプトは、学習とデータ削除を実行せず、`ability_advisor_v1/logs/ov1_attacker_advisor_score_review.json` に集計を保存する。
