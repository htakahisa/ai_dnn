## コード上の原因

`ov1_defender_controller.py` の `decide_move()` は、リテイクモデルを呼ぶ前に `recon_response()` を呼ぶ。`recon_response()` が行動を返した場合、守備窓口はその行動を即座に返し、そのキャラクターのリテイクモデルを呼ばない。

`ov1_inference_recon_response.py` は、自分の座標が公開されている場合、退避・遮蔽位置での待機を選ぶ。既存の解除緊急判定と敵の失明中の例外はあるが、この回避処理は、リテイクモデルの移動・アビリティ判断を止める。エンジンの自動射撃は、返した行動で射撃可能な場合に継続する。

通常条件では、この上書きが1マップ目のリテイク中に延べ244回、2マップ目のリテイク中に延べ276回発生した。各回数はキャラクター単位の判断回数であり、チーム単位の経過tick数ではない。

保存リプレイでは、omoko v1 は守備の14敗中8敗で、守備キャラクターが1〜3人生存したまま爆発を迎えた。たとえば、seed 3338407445 の第17ラウンドでは、複数の守備キャラクターが右サイト入口付近に滞留し、解除地点へ到達できなかった。第20ラウンドでは、守備キャラクター3人が生存したまま解除が間に合わなかった。

私は、設置後のリコン対応がomoko v1のリテイク性能を低下させる原因であることを比較で確認した。私は、今回の調査で本番の守備処理やモデルを変更していない。
