# Original v1：基本構成とAI設計方針

## 目的と現在の段階

- このゲームの5対5対戦で、強化学習を中心に、複数タイプの相手へ対応できるAIを作成する。
- 目標は、特定の相手だけに強いAIではなく、幅広い相手に安定して強いAIとする。すべての相手への勝利を保証するものではない。
- 現在はマップ定義と基本方針を整理した段階。学習方式、観測・行動の構造、報酬、モデル分割は今後設計する。以下の構成案を実装済み・性能確認済みとして扱わない。
- 親ディレクトリの `../AGENTS.md` の配置・設定・実行ルールも適用する。
- attacker plantの設計・実装・引継ぎ時は、[plantの基本方針と引継ぎ](doc/org1_attacker_plant_policy.md) を必ず確認する。作戦を選ぶ上位policyと5人で共有する下位policy、複数入口の時間連携、途中変更・再突入・左右ローテートを出発点とする。未確定事項と実装・学習済み事項を区別し、方針変更は同文書へ記録する。
- 新AIの設計・実装・評価時は、共通知見の [MODEL_BUILD_BASE_POLICY.md](../touyama_v3/docs/MODEL_BUILD_BASE_POLICY.md) を確認する。不具合確認、コード修正、教師改善、学習済み性能の改善を区別し、他AIの結果をこのAIの実績として扱わない。

## 3つのマップの役割

3ファイルは同じ座標系の注釈として重ね合わせる。基本盤面の役割は `org1_map_base.py` を正とし、分岐・サイトマップから基本盤面を再生成しない。

| ファイル | 役割 |
| --- | --- |
| `org1_map_base.py` | 基本盤面。床・壁・プラント可能位置・スポーン・オーブ・setup時の壁を定義する。 |
| `org1_map_branch.py` | 移動可能な通路の分岐点・分岐領域をアルファベットで定義する。 |
| `org1_map_site_border.py` | 左のAサイト、右のBサイトの領域を定義する。プラント可能位置とは別の範囲である。 |

### 基本盤面

- `0`：床。
- `1`：移動不可能な恒久的な壁。
- `2`：スパイクをプラント可能な位置。
- `3`：attackerのスポーン位置。
- `4`：defenderのスポーン位置。
- `5`：オーブの位置。
- `z`：setup phaseにのみ配置される移動不可能な壁。通常phaseの恒久壁として扱わない。

### 分岐マップ

- 同じアルファベットの複数セルは、一つの分岐領域として扱う。単一の代表座標だけに置き換えて通行・距離・射線の違いを失わない。
- 分岐マップは地形への注釈である。一部のオーブやsetup壁が文字・床に置き換わっていても、元の役割はbaseから取得する。
- 分岐間の接続・到達可能性・距離は、baseの実際の通行可能セルとphase条件で確認する。文字の並びだけで接続を推定しない。
- 分岐の `a` / `b` と、サイトマップの `a` / `b` は別の識別子として管理する。

### サイト領域と入口

- サイトマップの `a` はAサイト、`b` はBサイトへの所属を表す。これらは境界線だけでなく、サイト内部のセルを示す。
- サイトに入ることと、プラント可能位置へ到達すること、設置を完了することを区別する。
- サイトマップに残る `2` も該当サイトの内部に含める。現在は右のBサイトに `b` と `2` が混在するため、`b` だけの抽出では領域が欠ける。所属は明示的に管理し、左右半面の分類を一般的なサイト判定の代用にしない。
- オーブ・setup壁などはサイトマップでは省略されている。baseの情報を保持する。
- 入口は、移動で横断できる「サイト外セルとサイト内セルの境界」として定義する。幅のある入口は複数の境界セル対として保持できるようにする。
- サイト内から開始する経路には、入口横断がないことを明示する。
- 接近・突入・設置後・retakeなどの段階に応じて経路条件を分ける。サイト内部を横切る近道を、サイト外から入口までの接近路と混同しない。一律にサイト内移動を禁止することもしない。

### 初回確認の記録

2026-10-12の読み取り確認では、3マップは26行×44列で恒久壁の位置が一致し、baseの全プラント可能位置が対応するサイト領域内に収まっていた。

上下左右の隣接と恒久壁だけを考慮すると、サイト内外をつなぐ境界セル対はAサイトが2か所、Bサイトが3か所だった。これは現在の定義の確認値であり、固定の期待値として埋め込まない。setup壁・占有などを含む実際の通行可否は別に判定する。

## 地形情報と学習の分担

- 人が与える情報は、分岐・通路・サイト・入口などの地形の意味と接続関係とする。
- AIは、公開観測と記憶を使い、どの地形・経路をどう使って勝つかを学習する。
- 地形の接続を一から発見する負担を減らし、経路選択・入口突破・チーム連携へ学習を集中させる設計を目指す。学習効率・勝率への効果は検証が必要。
- 「ここが入口」「ここから射線が通る」という地形情報と、「今ここが安全」「敵がいない」という状況判断を分ける。安全な入口・攻撃先・退避先を恒久的に固定しない。
- 相手AI名による専用対策へ依存するより、観測した進攻・配置・能力使用などから対応を変える設計を基本とする。

## 戦術判断の構成案

- 上位判断では、サイト・経路・入口・味方の役割を選ぶ。
- 下位判断では、実際のグリッドと上位目標を使い、移動・向き・能力使用・設置／解除に関する行動を選ぶ。射撃はゲーム側の自動処理に従う。
- 分岐の接続図だけで判断を完結させない。同じ通路内でもセル・向きによって射線、遮蔽、味方の通行が変わるため、局所判断には実盤面を使う。
- 新しい敵の目撃、入口の詰まり、能力の変化、時間不足などに応じて再判断できる構成を検討する。入口変更時は、経路・集合位置・役割目標を整合させ、古い目標を残さない。
- 各段階の成功を区別する。安全な接近や入口突破、設置成功だけをラウンド勝利と呼ばない。

## 学習と行動制約の基本方針

- 行動は基本的に学習モデルが候補から選ぶ。BFS・距離・射線計算などは、到達可能性確認、特徴量、候補生成、教師例作成に使う。
- エンジン上の不可能な行動と、合法だが戦術的に危険な行動を区別する。危険度を理由に無条件で候補を禁止したり、推論時に前進・停止・突入・能力使用を強制して学習不足を隠したりしない。
- 戦術上の制約が必要な場合は、理由・条件・例外・候補消失時の扱いを明記し、学習と通常推論で一致させる。
- 敵の真の非公開位置や状態を、モデル・教師の判断へ渡さない。公開観測、観測の鮮度、記憶、確認済み不在を区別する。事後の診断・採点情報とは分離する。
- 模倣学習で基本動作を準備し、その後に強化学習で改善する方式を候補とする。特定アルゴリズムの採用はまだ確定していない。
- ラウンド勝利を最終目標とし、設置・解除・支援などの補助報酬が、往復・待機・作業の開始中断・不要な追撃を有利にしないよう設計する。
- 既存の複数AI、過去の自分、苦手な戦術を含む相手群との学習を検討する。自チーム編成を固定した初期検証も候補とするが、具体的な編成・相手群は未確定。

## ディレクトリ構成

追加するファイルは、`original_v1/` 内の次の用途別ディレクトリへ配置する。

| ディレクトリ | 用途 |
| --- | --- |
| `doc/` | 追加するドキュメント類。設計・調査・変更・検証などの作業内容を記録する。 |
| `test/` | 追加したテストコード・テストケースを残す。 |
| `evaluation/` | AIの評価に使用するPythonファイルなどの関連ファイルを配置する。評価ログは `logs/` に保存する。 |
| `lerning/` | 推論用のPythonファイルなどを配置する。ディレクトリ名はユーザー指定の `lerning` を使用する。 |
| `data/` | 学習データ・学習済みモデル・チェックポイントを保存する。 |
| `logs/` | 学習・評価などのログを保存する。 |

学習スクリプトは `original_v1/` に配置し、推論ファイルと区別する。必要なディレクトリは作成時に用意する。既存の3つのマップは現在の配置を維持する。

## 実行ログとcredit消費の抑制

- この節の出力・読み取り量の抑制は、エージェントがコマンドを実行したりログを読み込んだりする場合に適用する。
- ユーザーが通常の学習コマンドを実行し、コンソールのログで進捗や結果を確認する運用は従来どおり維持する。この方針を理由に、学習スクリプトの通常のコンソール表示を削減・無効化したり、ファイル出力だけに変更したりしない。
- エージェントが評価スクリプトやPythonコマンドを実行する際は、大量のログをそのままツール出力へ流して全文を読み込まない。credit消費を抑えるよう、出力量と読み込む範囲を工夫する。
- 大量の出力が予想される場合は、標準出力・標準エラーを `logs/` 内の実行ごとのファイルへ保存する。必要な結果・集計・エラー・失敗前後だけを `rg`（利用できなければgrepやPowerShellの `Select-String`）で検索・抽出する。
- 抽出時も件数・前後行・出力サイズを制限する。全ログの再表示や、同じログの繰り返し読み込みを避ける。短い結果要約を出す専用コマンドや集計処理も活用する。
- 出力削減のためにエラーを捨てたり、途中で切れた出力だけで成功と判断したりしない。終了コード、評価件数、完了状況、必要な評価指標を確認し、詳細ログはファイルに残す。
- ユーザーへの報告は主要な結果とログの保存先を中心にする。詳細調査が必要なときだけ、該当箇所の読み取り範囲を広げる。
- このログ運用は、学習を自動実行する許可を意味しない。学習は引き続きユーザーが実行する。

## 評価・互換性・実行

- 平均勝率だけでなく、相手別・攻守別・サイト／入口別の成績と、苦手な相手への勝率を確認する。率には母数も添える。
- モデル選定用と最終検証用のseedを分け、可能なら学習に使わない相手でも評価する。通常モデルの実力は教師・学習用探索なしで確認する。
- AIの判断力の比較では、編成・キャラクター性能・開始条件を揃える。地形注釈の追加だけで性能改善を確定しない。
- マップ、観測・行動の意味、射線、シナリオ、依存モデルを変更した場合は互換性と再学習範囲を確認する。版やhashを書き換えて不一致を隠さない。
- 現行の壁射線判定は `grid_lines.py` の `wall_line_cells()`、識別子は `WALL_LOS_VERSION = 'symmetric_supercover_v1'`。通常の `line_cells()` と用途を混同しない。
- 新AIのファイル・モデルは `original_v1/` 内にまとめ、既存Touyama v3などの定義・重みを、このAIの追加だけで変更しない。
- 新規ファイルは役割がわかる `org1_...` の名称とし、テストは `test/`、学習データ・モデル・チェックポイントは `data/`、ログは `logs/` に配置する。
- 新しい学習スクリプトは `original_v1/` を作業ディレクトリとして、通常はオプションなしで実行できるようにする。常用設定は冒頭の名前付き定数にまとめる。
- 学習はユーザーが実行する。学習の自動実行はせず、実行前に設定場所・作業ディレクトリ・通常コマンド・再学習範囲・停止条件・評価方法を説明する。
