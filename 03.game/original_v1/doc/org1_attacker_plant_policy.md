# Original v1：attacker plantの基本方針と引継ぎ

作成日：2026-10-12。

## 合意と現在の段階

ユーザーと、以下の階層構成を出発点としてattacker plantを作成する方針で合意した。本書は別スレッドで設計・実装を引き継ぐための記録である。

現在は方針の文書化段階。plantモデル、学習環境、報酬、教師、評価コードは本件としてまだ実装・学習していない。ユーザーの今回の依頼は文書作成とAGENTS.mdへの参照追加であり、学習の実行許可ではない。

作業前に [../AGENTS.md](../AGENTS.md) と、共通知見の [MODEL_BUILD_BASE_POLICY.md](../../touyama_v3/docs/MODEL_BUILD_BASE_POLICY.md) を確認する。

## 学ばせたい行動

- マップの分岐を5人一団で進む。
- 必要に応じて途中で分隊へ分かれ、複数のサイト入口へ向かう。
- 異なる方向からの能力支援と射線を同じ有効時間に重ね、孤立した先行突入を避けながらサイトを突破する。
- 支援役がキャリアーの進路・設置位置を確保し、設置へつなげる。
- 公開された敵・味方・能力・時間の変化に応じて、入口変更、退避後の再突入、別サイトへのローテートを判断する。
- 強い分隊攻撃だけでなく、一団で攻める方がよい状況も学ぶ。分隊化・同時能力使用そのものを目的にしない。

Touyama v3ではanalysisから経路などを指示し、途中の入口変更・再突入・左右ローテートを扱っていた。その適応の考え方と失敗調査の知見を引き継ぐが、既存モデルをそのまま移植する方針ではない。

## 基本構成：作戦判断と実行判断の2階層

初期版は、作戦を選ぶ上位policyと、5人で共有する下位policyを、plantの一つのシステムとして構成する。下位policyは各人の役割・状態・目標を区別して行動を選ぶ。共有policyを使うことは、全員が同じ行動をすることを意味しない。

| 層 | 主な判断 |
| --- | --- |
| 上位：チームの作戦 | サイト、経路、分隊構成、各分隊の入口・役割、合流・突入・継続・変更の判断 |
| 下位：5人の実行 | 移動、向き、能力の投擲先とタイミング、援護、退避、設置に関する行動 |

射撃はゲーム側の自動処理に従う。AIは向き・位置・能力などを通じて射線と戦闘を成立させる。

最初から独立したanalysis成功予測モデルを先に作るより、上位policy自身が作戦を選び、実際のplant実行結果で改善する構成を出発点とする。予測を生成した実行役と現在のplantの実力が異なる問題を管理しやすくする狙いであり、性能改善が検証済みという意味ではない。補助予測やcriticの採用を禁止するものでもない。

## マップ情報の利用

- 基本盤面は `../org1_map_base.py`、分岐領域は `../org1_map_branch.py`、サイト領域は `../org1_map_site_border.py` を使う。
- 人が与えるのは地形の意味・接続関係。AIはその使い方と戦術を学習する。
- 分岐・通路・サイト外／内の境界を使って、到達可能な経路と入口の候補を作る。
- サイト領域、入口横断、プラント可能位置、設置完了を別々に扱う。
- 接続図は大きな経路選択に使い、局所行動には実際のグリッド・向き・射線・遮蔽・味方の通行を使う。
- 接近中にサイト内部を横切る近道を、入口までの接近路と混同しない。突入後・退避・再突入などの段階に応じて経路条件を設計する。
- setup壁の扱い、入口の幅、分岐領域とサイト領域の識別などはAGENTS.mdのマップ契約に従う。

## 初期の作戦候補

全員の分隊所属と全経路を最初から自由に組み合わせると候補が大きくなるため、初期版は少数の構成と、到達可能な経路・入口の組合せから選ぶ。

- 5人一団。
- 3＋2、4＋1などの分隊構成。
- 途中まで共通経路で進み、分岐から別入口へ向かう作戦。

上記は初期候補の例。採用する構成、役割割当、候補数、経路生成方式は実装前に具体化する。特定の構成・サイト・入口を常に選ばせるルールにはしない。候補制限が有効な戦術を落としていないか診断する。

## 複数入口の連携とタイミング

目標は、複数の入口へ到達することだけでなく、別方向からの攻撃が同じ有効時間に重なること。

- 一方の分隊だけが先に露出しない。
- FLASHの効果中に味方が射線を作れる。
- SMOKEが敵の射線を切りつつ、味方の反撃・能力作用を妨げない。
- キャリアーが設置できる通行・位置を支援役が確保する。

観測・特徴量の候補として、各分隊の入口までの残距離と到着見込み、味方の準備状況、公開敵への射線、能力残数、投射飛行・効果時間、移動と設置の残作業、ラウンド残時間を検討する。

「全員が入口に着いたら必ず突入」「能力を固定順で使う」という強制手順にしない。今の人数で入る、能力を待つ、支援位置を変える、別案へ変更する判断を学習対象にする。到着見込みは通行・占有で変わり、能力作用は未知敵への成功を保証しない。

## 途中変更・再突入・ローテート

- 入口変更と左右ローテートを後付けにせず、初期設計から目標更新と時間比較を扱う。
- 上位が毎tick無条件に作戦を変更すると往復しやすいため、通常は短い区間を同じ目標で実行し、状況変化で再判断する構成を候補とする。
- 再判断の契機には、新しい敵の目撃、分隊到着、味方死亡、能力の変化、通路の詰まり、時間不足などを検討する。契機・周期・継続条件の具体値は未確定。
- 変更時は、経路・入口・集合位置・分隊／役割目標を整合させ、古い目標を残したり翌tickに再割当したりしない。
- ローテートでは、新サイトまでの移動・準備・突破・設置に必要な時間を比較する。安全な迂回や正当な退避を停滞と誤判定しない。
- 到達可能だが危険な候補と、物理的／段階上到達不能な候補を区別する。

## 段階的な学習方針

1. **入口突破の基本**：短い局面から、一団での接近、射線を作る移動、能力支援、キャリアーの設置を学ぶ。
2. **複数入口の連携**：分隊ごとの距離・到着時刻が異なる局面も使い、待機・支援・突入のタイミングを学ぶ。
3. **スポーンからの作戦選択**：一団と分隊の使い分け、途中の入口変更、再突入、左右ローテートまで広げる。
4. **複数相手との通し検証**：左右・入口別の失敗、死亡、時間切れ、設置後の状態を確認する。

短い局面での成功だけで通し対戦の強さを判断しない。上位と下位の具体的な更新順、同時更新／交互更新、模倣の利用、強化学習アルゴリズム、学習量は未確定。各段階の結果を見て具体化する。

## 報酬と評価

- 分隊数や同時能力使用そのものへ大きな報酬を与え、形だけの連携を目的化しない。
- plant段階では設置成功と設置時の状態を評価する。複数方向の射線や能力の重なりは、まず診断指標として記録する。
- 設置前に敵を全滅させて実際に勝ったラウンドも、未設置だけを理由に失敗扱いしない。
- 設置成功・設置品質とラウンド勝利を区別する。将来guardへ接続した際は、実際の勝利へつながるか確認する。guardの初期接続先は未確定。
- 往復、作業開始／中断、待機の先延ばしで報酬を稼げないようにする。具体的な報酬式・重み・best選定基準は今後設計する。
- 評価では相手別・左右／入口別の件数と成績、一団／分隊の選択と実行、実入口、設置時の人数・状態、死亡・時間切れを確認する。
- 作戦を選んだ回数と、実際にその経路・分隊・入口を実行した回数を区別する。
- 途中変更の理由と変更後の結果、能力要求・受理・着弾・公開効果、援護射線の成立と時間関係を記録する。非公開の事後診断情報は行動入力へ戻さない。
- 教師・学習用探索なしの独立評価で判断し、モデル選定用seedと最終検証用seedを分ける。自チームと相手の編成・性能差も記録する。

## 実装前に具体化する事項

- 自チーム編成、キャリアー、対象相手群と初期検証の範囲。
- 上位の作戦表現、分隊・役割割当、経路・入口候補の生成と制限。
- 下位の共有policyへの役割入力、観測・記憶、5人の行動選択と衝突処理。
- 作戦継続・再判断の条件、段階境界、設置／終了時の扱い。
- 能力候補、射線・支援・到着見込みの定義と実エンジンとの整合。
- 学習環境、教師、アルゴリズム、上位／下位への結果の帰属、報酬、更新スケジュール。
- 評価条件、ログ、保存形式、schema・マップ・依存モデルの互換性。

## 別スレッドでの再開手順

1. `original_v1/AGENTS.md`、本書、共通知見を読み、3マップと実エンジンの契約を確認する。
2. 上記の未確定事項を整理して具体的な設計へ進む。2階層、途中変更、複数入口の時間連携という基本方針を引き継ぐ。
3. 設計変更・調査・実装・検証結果は `doc/` に残し、方針が変わった場合は本書も更新する。実装確認と学習済み性能を区別する。
4. テストは `test/`、評価用コードは `evaluation/`、推論ファイルはユーザー指定の `lerning/`、学習データ・モデルは `data/`、ログは `logs/` に置く。学習スクリプトは `original_v1/` に置く。
5. 学習はユーザーが実行する。学習前に冒頭定数の設定場所、作業ディレクトリ、オプションなしの通常コマンド、停止条件、評価方法を示す。
6. エージェントが評価などを実行する際は大量ログをファイルへ保存し、必要箇所だけ `rg` などで抽出する。ユーザーの通常学習時のコンソール表示は維持する。

本書作成時点でコード実装・学習・性能評価は行っていない。既存Touyama v3や他AIのマップ・モデル・重みは変更していない。
