# Toru AI v4：attacker analysis の方針と学習

## 目的と責務

現在の観測・判断・学習ラベルの設計は [attacker_online_design.md](attacker_online_design.md) を参照する。開始時の経路固定を撤廃し、analysisの収集・評価とplantに同じオンライン再評価を接続した。

公開観測と相手AIの傾向から敵の配置を推測し、どの道を通ってどちらのサイトへ入れば、被害とアビリティ消費を抑えてプラントできるかを評価する。相手AIごとに独立した解析モデルを作る。

将来の attacker（プラント）モデルは、解析結果と味方状態・残り時間を入力にして、移動、アビリティ使用、プラントを実行する。今回学習するのは解析であり、この行動モデルそのものではない。attacker guard、プラント後の配置、守備用アビリティを残す評価は対象外とする。

defender analysis と同様に、FRCの公開チーム観測、観測履歴、相手別モデル、同じ対戦AIを維持する12ラウンドの学習セット、独立seedの評価、latest/best保存を使う。defenderの左右二択分類器の重みは流用せず、attacker用の出力を持つモデルを学習する。

## 実装した解析

- 入力は、分岐領域の目撃・監視・無人確認、敵別の最終目撃位置・移動差分・情報の古さ、味方の位置・HP・生存・アビリティ残数・能力種類・射撃性能・最大HP・ult情報・スパイク所持・設置進捗、残り時間、ラウンド番号、過去ラウンドの公開結果。
- 敵ごとに `a`〜`n` の領域と死亡状態の確率分布を出力する。領域は、マップ上の文字そのものだけでなく、実通路距離で最も近い分岐に割り当てた区域を意味する。1マス単位の敵位置を断定するモデルではない。
- 現在公開されている目撃と死亡情報は、推論APIの配置分布に確定情報として反映する。生存中の敵に死亡確率を割り当てない。評価ログの配置正解率は、こうした確定情報による補正前の学習ヘッドの性能を測る。
- 候補の経路・進入方法ごとに、プラント成功確率、今から終了までの追加HP被害、追加死亡人数、追加アビリティ使用回数、成功した場合のプラントまでの残りtickを予測する。
- 敵が道上にいる場合に加えて、最後に目撃した場所から経路へ射線が通る度合いと情報の古さを経路特徴に含める。未観測の場所は無人と扱わない。
- 推測の不確かさとして配置分布のエントロピー、学習済みラウンド数を返す。エントロピーは配置の曖昧さであり、経路成功率の校正済み信頼区間ではない。

隠れた敵の実座標・内部目標・未公開スパイク所持は、入力、経路選択、収集用の行動には渡さない。敵の実配置は、公開入力と行動を確定した後、学習側だけが教師ラベルとして記録する。配置推測も経路評価も、実行時は公開入力だけで計算する。

## 経路と往復防止

`tv4_map_attacker_branch.py` の文字を本番マップへの注釈として読み、壁・オーブ等の地形は本番マップを使う。文字間に架空の接続は作らない。

現在地から各サイトへの最短経路と、分岐領域の代表地点を経由する経路を、実際に隣接する通路マスで生成する。経路内に同じマスが再登場する候補を除外し、分岐領域の通過順で重複を除いて、短い順に各サイト最大6候補を残す。サイトから一時的に離れる遠回りも残り時間内なら選べる。この方式は候補数を制限した探索であり、すべての経路からの最適性を保証しない。

移動歩数 + エンジンのプラント必要tick + 5tickの余裕が残り時間を超える候補は除外する。これは障害や戦闘待ちを含まない最低所要時間による除外であり、実際の時間切れも失敗データに残す。

収集用の実行器は経路へ進みながら、各味方が射撃できる公開目撃・新しい目撃履歴に応じて停止射撃する。失明・低HP・複数射線では短い退避、単独の角出しでは最大6tickの援護待ちを使う。利用できる別入口には非所持者2人を分ける。初期位置から経路への接続、落ちたスパイクの回収は別途行う。進入後は所持者の経路を空けながら戦闘する。

## 進入方法と収集用実行器

同じ経路を次の2種類で評価する。

| mode | その判断時点での進入支援 |
|---|---|
| `preserve` | 先制使用を控えて移動・射撃・プラントを行う。交戦への反応は許可する |
| `supported` | 公開目撃・学習した配置予測と合法アクションマスクに基づいて通常アビリティを使用する |

`supported` は、サイトの近くで未目撃ならRECON、複数目撃ならSMOKE、近い目撃対象にFLASH、合法範囲の目撃対象にASH、回復できる味方にDANCEを使用する。その他のアビリティとULTは今回の収集器では使用しない。射撃・被弾・移動・設置のルールは既存エンジンのまま。

加えて、学習済みモデルが敵の存在を高確率で予測したエリアには、視認前にもFLASH・SMOKE・RECON・ASHを使用できる。通常設定は `tv4_attacker_entry_utility.py` 冒頭の定数（配置確率0.65、近傍経路8マス、経路からの脅威距離4マス、投げ先距離10マス）。最低カバー割合はFLASH=0.4、RECON=0.2、SMOKE/ASH=0.1。エリア全体の未知マスを分散サンプリングし、経路の近くに敵が集中しているとは仮定しない。未学習・曖昧な予測、視認済みの無人マス、進行経路に射線が通らない場所、非合法な投げ先は先制使用の対象外。実際の敵座標やFRC固有の配置番号は参照しない。

FLASH・RECONは指定地点で停止する投射物ではないため、公開マップの壁とエンジンの飛行速度から着弾・炸裂位置を計算する。収集器は1tickに1人だけ先制使用し、投げた本人以外は進行を続ける。リコン・スモークは全員の待機理由にしない。フラッシュは飛行終了前に遮蔽物から射線へ出る直前だけ待ち、既に露出している場合は近くの遮蔽物へ移る（合法な遮蔽物がなければ通常の進行を続ける）。スパイク所持者の今後の経路に対する脅威に投げ先を限定し、各エリアのカバー割合で比較する。敵に命中したという確定情報は使わない。JSONの `entry_utility` に投げ元・投げ先・フラッシュ炸裂見込み位置を、`entry_cover` に実際の遮蔽物での待機・移動を記録する。

同種1回/ラウンドの制限は撤廃。チーム共通の `SupportUseTracker` で、同種の飛行・効果表示中および使用後4tick以内の重複を抑える。その後は、所持者の位置が4マス以上進んだ、新しい敵IDを視認した、投げ先が4マス以上変わった、前回の効果の見込み時間が経過した、のいずれかで追加使用できる。効果終了の目安はFLASH=15tick、RECON=20tick、SMOKE=25tick、ASH=10tick。これらの通常設定は `SUPPORT_REUSE_COOLDOWN`・`SUPPORT_REUSE_DISTANCE`・`SUPPORT_REFRESH_TICKS` にまとめ、目撃への反応と先制使用で共通に使用する。残数と合法マスクは引き続き確認する。plantの推論では学習済み方策が使用回数を選ぶ。

plant側も同じ予測・投射計算による合法な投げ先を行動候補に追加し、支援あり進入の教師例に先制使用とフラッシュ飛行中の遮蔽物での待機・移動を含める。推論時の使用・待機はplantの学習済み方策が選び、配置予測だけで行動を強制しない。

現在の実行器は `public_online_combat_attack_v7`、plantの実行条件は `adaptive_combat_plant_v5`。analysis入力/schemaはversion 3、plant/schemaはversion 4。戦闘修正前のラベル・best評価と新条件を混ぜず、analysis → plantの順に新規学習する。`RESUME_TRAINING = False` をそれぞれの学習スクリプト冒頭で設定し、下記の作業ディレクトリから通常実行する。既存best/latestはコード変更だけでは更新しない。guardの保存ケース・モデルもanalysis/plantのhashに依存するため、新しいbestの完成後に再収集・新規学習する。実測比較は [attacker_combat_review.md](attacker_combat_review.md) を参照する。

```powershell
Set-Location C:\Users\ronet\MyProject\git\AI_dnn\03.game\toruAI_v4
python tv4_train_attacker_analysis.py
# analysis学習完了後に実行
python tv4_train_attacker_plant.py
```

**経路とmodeは公開情報に応じて更新する。** 通常3tickごと、被害・死亡時は即時、停止時は迂回を検討する。回数上限はなく、設置開始後だけ継続する。学習中の既定80%の探索は、観測に基づく判断時点で有力な候補間を選ぶ率であり、1ラウンドのサイトをランダムに固定する率ではない。各frameの結果ラベルは、その進路を選んだ後に観測で判断を更新した継続結果を表す。未実行経路の成功ラベルは生成しない。

この実行器は解析用データを集めるための基準手順。将来のプラントモデルが異なる移動・アビリティ手順を使う場合は、その実行結果で解析を再学習し、実行方式のschemaも更新する。

サイトに到着した非所持者は、所持者が通る経路を避けてサイトの奥へ進む。入口に最初の味方が停まって後続を塞いだ場合も、到着済みの味方をさらに奥へ動かして通路を空ける。移動先は味方の現在位置と予約先を避け、サイト入口からの距離が増える方向に限る。移動のために同じ場所を往復しない。入口の退避はアビリティより優先する。所持者は選択サイトとの一致と接触・失明・HP・援護を確認してから設置する。

入口渋滞の修正時点ではexecutor schemaを `fixed_route_public_utility_site_clearance_v2` とした。その後、オンライン再判断と戦闘修正を行い、現在は上記v7を使う。旧実行器の学習データには、味方による通路閉塞や戦闘動作の不備による失敗ラベルが含まれるため、旧latest/replayをそのまま再開しない。`tv4_train_attacker_analysis.py` 冒頭の `RESUME_TRAINING = False` で新規学習する。コード修正だけでは既存モデルを変更しない。新規実行では同じ通常保存先のlatest/bestを更新する。新analysisのbestが完成してからplant学習に進む。

渋滞検証では保存データにあった左右の配置を合成状態で再現し、衝突せずに所持者が到達・設置完了できることを確認する。また、妨害のない5人編成が既定の全候補経路で100tick以内に設置できることを確認する。戦闘修正では別途実エンジンの同条件対戦比較を行い、[attacker_combat_review.md](attacker_combat_review.md) に結果を記録した。

収集器とplantは `AdaptiveAttackPlanner` を共有する。視認した敵の移動、無人確認、味方の被害・死亡、停止に応じて再判断する。候補スコアには学習した配置分布からの敵存在確率を直接反映し、情報が乏しい間は短距離の観測目標も評価する。小さいスコア変動での変更は抑える。

## 学習と評価

入力の共通表現から、敵配置分類ヘッドと、経路特徴を追加した結果予測ヘッドを学習する。成功確率には二値分類、被害・死亡・アビリティ消費・時間には回帰を使用する。

プラントなし、全滅、時間切れ、敵全滅でラウンドが終了したケースも保存する。プラントなしに左右の成功ラベルを作ったり、架空のプラント所要時間を教えたりしない。時間回帰は成功ラウンドだけで行う。HP被害は各tickのHP減少を累積し、回復で差し引かない。学習値は追加被害500HP、追加アビリティ消費10回を上限として正規化する。

ラウンドを均等に抽出してから、そのラウンドのtickを選ぶため、長い失敗ラウンドだけが学習を支配しない。相手のモデルは更新しない。プラント完了tick終了時点、または未プラントのラウンド終了時点を評価の終点とする。

プラント後は収集用attackerを待機させ、通常エンジンでラウンドを最後まで進めて、相手AIのラウンド間状態と公開勝敗履歴を維持する。この区間の被害・消費・勝敗は経路評価の教師・best評価には含めない。過去ラウンド入力の勝敗だけは通常の実際のラウンド結果を使う。

既定では10セットごとと最終セットに、共通の独立3seedで以下を行う。評価中は重み・optimizer・学習replayを更新しない。

- 解析で選んだ経路・mode：3seed × 12ラウンド。
- ランダムな経路・mode：別の3seed × 12ラウンド。偏りを抑えた予測誤差の確認にも使う。

合計72評価ラウンドを集計する。成功率、生存人数、HP被害、アビリティ使用回数、成功時のプラントtick、時間切れ数を記録する。ランダム評価では成功確率のBrier誤差、敵配置の正解率、各回帰値の平均絶対誤差も出す。

学習・評価ログには、プラント成功率、敵味方それぞれの生存率と平均生存人数、通常アビリティの温存率・使用率と平均使用回数も百分率で表示する。集計時点はプラント完了tick終了時、失敗ラウンドでは未プラント終了時であり、プラント後の戦闘を含まない。

**解析モデルの性能を見るには、コンソールで緑色に表示する `[実力評価]` の「プラント成功率」を確認する。** 公開観測・オンライン再判断を使い、ランダム探索を含まない収集器での実測値。経路再評価・サイト変更の回数も表示する。plantの学習済み局所行動の成績や、未知の全配置に対する保証値ではない。評価JSONは配置正解率に加え、未視認の生存敵だけの `unseen_placement_accuracy` を記録する。

実力評価の行だけを明るい緑色にし、通常の収集行は標準色で表示する。色設定は学習スクリプト冒頭の `COLOR_CONSOLE` と `EVALUATION_CONSOLE_COLOR` で変更できる。WindowsではコンソールのANSI表示を有効化する。ファイル保存や出力リダイレクトには色の制御文字を含めず、色を使えない端末では標準色で表示する。★マークは使わない。

毎セットの行は `[データ収集][ランダム探索率=80%]` とし、その率を「収集プラント成功率」と表示する。ここは危険な候補の結果も集めるので、モデルが改善しても低い率が出る。各収集行に「直近の実力評価」と、その評価セット番号を併記する。例えばset=48の行にset=40の評価を載せた場合、それは48セット目のモデルを測定した値ではない。

直近の評価はlatestに保存し、再開時も表示する。旧形式latestにはこの記録がないため「未記録（次の評価で表示）」とする。再開時は保存bestの成功率と採用セット番号も別に表示し、直近評価と混同しない。ランダムだけの評価は `[比較評価][ランダム探索100%]` と表示する。変更済みログ表示はスクリプトの次回起動から適用される。

- 生存率：集計時点の生存人数の合計 ÷ ラウンド開始時の人数の合計。
- アビリティ使用率：プラントまで、または失敗終了までに使用した通常アビリティ回数の合計 ÷ 開始時の残数の合計。
- アビリティ温存率：集計時点に生存者が使用できる通常アビリティ残数の合計 ÷ 開始時の残数の合計。死亡者が未使用のまま失った残数は温存に数えないため、使用率と温存率の合計が100%未満になる場合がある。

開始時のアビリティ残数が0なら温存率・使用率は「対象なし」と表示し、JSONではnullにする。ULTは今回の使用率・温存率の集計に含めない。seed別の率を単純平均せず、全ラウンドの分子・分母を合計して計算する。

経路APIの既定scoreは、成功確率から死亡・被害・消費・時間の小さな重み付き負担を引く。アビリティ消費だけを最小化する目的にはしない。bestモデルの採用は、3人以上生存かつ開始時チーム最大HPの30%以上を残した設置率 → 通常設置率 → 生存人数 → 少ない被害 → 少ない消費 → 短い成功時間 → 小さいBrier誤差、の順で比較する。残りHPも別に表示する。この生存条件は設置後勝率の予測ではなく、全滅寸前の設置を優先しないための基準。これは異なる経路の反実仮想を完全に測定した「最善経路」の教師ではなく、実際に実行した経路の結果を学習する方式。

## 通常実行

作業ディレクトリは `03.game/toruAI_v4/`。通常設定は **`tv4_train_attacker_analysis.py` 冒頭の名前付き定数**で変更する。

- `TRAINING_SETS`：相手ごとの追加セット数。既定30セット = 相手ごと360学習ラウンド。
- `TARGET_OPPONENTS`：学習対象。既定は既存defender analysisと同じ6種類。
- `TRAINING_PRESETS`：複数の学習用味方編成。セットごとに切り替え、相手との選手名重複を除外する。
- `EVALUATION_PRESETS`：学習とは別の評価用味方編成。各評価seedで編成を固定して比較する。
- `RESUME_TRAINING`：`False`で新規学習、`True`で同じ保存先のlatestから再開。
- `EVALUATION_ONLY`：再開モデルの評価だけを行う場合に`True`。`RESUME_TRAINING`も`True`にする。
- seed、探索率、評価間隔、更新回数、保存先も同じ場所で指定する。

```powershell
Set-Location C:\Users\ronet\MyProject\git\AI_dnn\03.game\toruAI_v4
python tv4_train_attacker_analysis.py
```

新規学習では同名latest・セットデータを更新し、最初の評価でattacker analysisのbestを更新する。残っている古いセットファイルを自動で学習に混ぜることはない。再開時はschemaと収集・評価設定の一致を確認し、重み・optimizer・replay・完了セット数・抽出乱数状態を復元する。中断時は完了したセットまで保存済みで、未完了セットは保存しない。

CLIは一時的な検証用に定数を上書きする。通常運用は上の定数を変更してオプションなしで実行する。

通常は `MAX_PARALLEL_WORKERS = 3` で相手AIごとに並列学習する。ログは `logs/attacker_analysis/<相手AI>/training.log`。最大1なら従来の順次実行。設定は [並列学習](parallel_training.md) を参照する。

toru AI v4は汎用AIであり、通常学習を味方1編成に固定しない。旧版のGorigons固定で収集・評価した結果は、複数編成での学習済み結果ではない。旧固定編成checkpointを新しい複数編成条件として通常再開はできず、汎用版は新規学習する。既存モデル・データはコード修正だけでは変更しない。

現在のanalysis入力形式はversion 3。監視履歴、配置分布を使う経路特徴、適応的継続ラベルへ変更したため、旧checkpointは今回の形式で再開できない。起動済みプロセスにはコード変更が適用されない。新しい入力形式でanalysisを新規学習し、後段のplant、guard収集、guard学習も新bestに合わせて更新する。

```powershell
# マップ、入力schema、候補経路を表示するだけ
```

## 将来のプラントモデルへの接続

```python
from frc_v1.perception import FrcPerceptionBuilder
from toruAI_v4.tv4_scenario import Scenario
from toruAI_v4.tv4_learn_attacker_analysis import load_analysis

scenario = Scenario()
model, encoder, saved = load_analysis(
    "data/best/fnatic_v3/attacker_analysis_best.pt", scenario, "fnatic_v3")
sensor = FrcPerceptionBuilder("A")

# ラウンド開始ごとにsensor.reset()とencoder.reset()を呼ぶ。
# previous_roundsは、この試合で公開された過去のsite/winner履歴。
snapshot = sensor.build(game)
observation = encoder.observe(snapshot, previous_rounds)
analysis = model.analyze(encoder, snapshot, observation)
ranked_candidates = analysis["candidates"]
```

候補には `route.site`、`route.cells`、`route.branches`、`mode`、成功確率、予想追加負担、条件付き所要時間が含まれる。追加負担の終点はプラントまたは失敗終了であり、guardを含まない。候補が空なら時間内に実行可能な候補が作れなかった状態で、成功経路を捏造しない。

同じ公開snapshotについて観測を1回だけ更新し、同じ特徴から全候補を評価する。将来のプラントモデルはこの結果を判断材料として使い、実際の合法アクションと経路変更制約は行動側で管理する。

プラント用モデルの実装と学習手順は [attacker_plant.md](attacker_plant.md) を参照する。経路選択にはこのanalysisのbestを固定して使用し、左右の選択率を強制的に均等化しない。
