# 接近路・入口目標・アビリティの結合（2026-10-11、未解決）

危険入口の自律選択・成功予測の追加調査は [tv3_frc_risk_learning_review.md](tv3_frc_risk_learning_review.md) を参照。

**右サイト問題全体の解決、再学習準備完了とは判断していない。** 学習更新は0回。以下の成功例は経路を指定した教師診断であり、学習済みモデルの成績ではない。

## 安全側の接近と投擲は地形上可能

seed 804000042・第6ラウンド・33tickでは、公開された敵位置2,40だけを使い、設置役22,35から7,37まで43歩の壁遮蔽経路がある。煙・味方の身体・敵の向きには頼らない。7,37から4,40などへFLASHを投げると敵2,40へ効果が届く。実際の射線・アビリティ処理を使うテストでも、遮蔽位置から合法に投げて敵をブラインドにできる。

ただしこれは既知の敵に対する接近路。途中で別の敵7,38が見え、上側の接近も撃たれる状況になる。既知の敵を避ければ未知の敵もいない、とは判断しない。また、`Scenario.site_of()`は左右半面を返すだけなので、厳密な設置可能床への所属判定には使わない。

## 入口の隊列目標が以前の経路を上書きしていた

安全経路を選択した後も、設置役には以前の外周入口11,40が渡され、33〜35tickは東へ動いていた。`PlantSiteAssembly`はサイト変更時にリセットするが、同じサイト内で入口が変わっても以前の目標を保持した。また準備開始の距離も選択経路の残り距離ではなく、最寄り設置床への距離だった。

新規analysis v4では、入口が変われば隊列目標を作り直し、選択経路で入口が近くなるまで接近用の目標を維持する。診断では33tickから目標22,31・行動Wへ切り替わった。v3の挙動は維持する。前回の「逆方向へ動く」例には、距離報酬の偏りだけでなく、この古い目標の上書きもあった。

## 有効な角度の投擲候補が不足していた

遮蔽された8,31から既知敵7,38・2,40を狙う制御された状態で、v11はFLASH候補をすべて不適合とする。敵の位置や設置点へ直接向けても、実際の投射終点が敵を捉えないため。一方6,40へ向けたFLASHは両方に届く。

新規plant v12では、選択サイトの地形と公開された敵位置から有効な投擲候補を作り、既存8候補中の一部へ追加する。着弾位置・飛行時間・既知/現在視認の効果対象数を40入力で提示する。投げるかは学習モデルの選択。RECON等の候補や旧v9/v10/v11の定義はこの変更で置き換えない。

## FLASHが効いていても待機・退避していた

実行後の診断ラベルでは、右の敵2,40は87〜97tickにブラインドだった。その間も教師は入口手前で待ち、91tickに前進、92tickに退避していた。診断用に読んだ敵の内部状態は、行動判断には渡していない。

v12には、実行した味方投擲の弾数減少と公開FLASH着弾から推定する攻撃可能時間の2入力も追加した。推定には新しい敵位置、壁、着弾時の煙を使う。着弾時に煙で遮られた敵を、煙が消えた後にブラインドだったと扱わない。実行時も公開された味方の弾数から確認でき、学習用の実行後フックに依存しない。

教師の待機・退避をこの推定で変える試作も比較した。全キャラクターの物理状態、公開状態、Python/NumPy/コントローラ乱数を33tickで一致させ、同じ前半の教師実行から介入した結果：

| 介入 | 結果 |
| --- | --- |
| 対照 | 時間切れ、2人生存 |
| 安全経路の指定だけ | 時間切れ、5人生存 |
| 安全経路＋入口目標の修正 | 時間切れ、4人生存 |
| 上記＋v12候補・攻撃可能時間の試作教師 | 94tickに設置、4人生存 |

最後の例では87tickから前進し、90〜93tickに設置動作を行う。同一状態の比較は `covered_corner_window_comparison.json`。経路指定と教師による診断であり、自律的にその経路を選んだ勝率ではない。

**攻撃可能時間で教師の判断を変える試作は、通常学習では無効に戻した。** 診断でのみ `experimental_flash_teacher=True` を使用する。v12の候補・推定入力は残すが、良い局所例を根拠に不良な教師を学習へ採用しない。

## モデル契約と未解決点

### 追加調査：分岐と入口の接続、サイト内を横切る距離計算

右リテイク図の入口A/B/Cはそれぞれ(2,37)/(7,37)/(11,40)。attacker分岐の小文字b/d/hと混同しない。設置床を通らない実経路で調べた結果、Cはbから11歩・dから6歩・hから3歩で到達できた。したがってCを「接続不能」として一律に除外する根拠はない。既知敵(2,40)の壁射線が通るため、到達性と危険性を分ける必要がある。接続監査は `logs/attacker_route_risk_review/entry_connectivity.json` に保存した。

追加で、(11,40)→B(7,37)の距離が通常盤面では7歩、両サイトの設置床を通らない盤面では25歩となることを確認した。前回のv4修正にもこの通常盤面による近道が残っており、選択した接近路の残距離を過小評価して入口準備を始める条件があった。接近距離をサイト床を通らず算出するよう修正し、同地点から別入口へ向かうケースをテストした。

新規v4の迂回役には、サイト床を通らない到達性と設置までの残り時間を確認する。以前の入口が主入口になった場合も迂回目標を解除する。拒否理由はplannerイベントの `rejected_entry_assignments` に `outside_path_unreachable` / `entry_deadline` / `now_primary_entry` として記録する。これは物理的な接続・時間の検証であり、既知射線を理由に全ての危険入口を消す変更ではない。既存v3の条件は維持した。到達不能や期限超過の割り当ては制御されたテストで検証しており、実際の対象ラウンドで発生した主原因とまでは断定しない。

修正後の実動作診断は `entry_connectivity_revision_labels_corner_teacher_summary.json`。経路指定と実験教師による94tick設置・4人生存を再現した。既存v3/v10の記録と採用重みhashは保存参照と一致した。学習は実行していない。新規v4のschemaにも接近距離・迂回役検査の契約を記録し、前回の試作schemaと区別する。

## 再現

設定は各スクリプト冒頭の名前付き定数。作業ディレクトリは `03.game/touyama_v3/`。

```powershell
python tv3_review_attacker_route_risk.py
python tv3_review_attacker_safe_entry.py
python tv3_review_attacker_covered_approach.py
python tv3_review_attacker_entry_candidates.py
```

3番目の既定は採用モデルによる経路・目標の診断。教師比較を通常実行する場合は冒頭の `POLICY_MODE='corner_teacher'` にする。一時比較は `python tv3_review_attacker_covered_approach.py --mode corner_teacher`。学習は行わない。結果は `logs/attacker_route_risk_review/`。

全体の候補追加だけの比較は `python tv3_review_attacker_right.py --mode corner_teacher --prefix corner_geometry_36`。既存比較の結果は `logs/attacker_right_review/corner_teacher_36_summary.json` と `corner_geometry_36_summary.json`。
